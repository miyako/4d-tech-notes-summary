This Technical Note (25-10, published October 31, 2025) documents 4D's "Force Login" REST authentication model, the default in new projects since 4D 20 R6, which requires users to sign in before performing protected REST/Qodly actions and replaces the deprecated legacy "On REST Authentication" database method. New projects automatically generate a `roles.json` file in the Sources folder with `forceLogin: true` and a default `"none"` privilege that denies all access (a deny-all, explicitly-grant-what's-needed posture); existing projects migrate via the "Activate REST authentication through ds.authentify() function" button in Settings → Web → Web Features, which removes legacy group permissions, deactivates the old method, and generates `roles.json` if missing (simply hand-editing the file is explicitly insufficient). The workflow is three-step: an initial REST request automatically creates a privilege-less, license-free "guest" session that can only issue descriptive requests (`/rest/$catalog`, `/rest/$catalog/authentify`, `/rest/$getWebForm`); the developer implements an exposed `authentify()` datastore class function that validates credentials and calls `Session.setPrivileges()` to grant real access (the note shows three implementation options — open/Administrator access, mapping legacy 4D user groups, or a fully custom user-management table); and only a successful `authentify()` call consumes a 4D REST/Qodly license, decoupling authentication from license usage. Access control itself is expressed in `roles.json` via privileges, permission actions (create/read/update/drop/execute/promote), and resources (datastore, dataclass, attribute, data-model/singleton function), each independently checked on every request, and can also be managed through a visual Qodly "Roles and Privileges" interface. The note works through a full worked demo (a "Company" dataclass with an "AccessTOCOMPANY" privilege), including custom `ds.hasPrivilege()`/`ds.getPrivileges()` checks gating admin-only class functions, and REST examples for fetching, creating, updating, and deleting records under this permission model, concluding that Force Login provides a secure-by-default, explicitly-permissioned foundation aligned with modern web-security practice.
