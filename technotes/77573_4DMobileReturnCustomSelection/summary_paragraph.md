This Tech Note addresses a specific limitation of the native 4D command "Mobile Return selection," which converts a selection of records from one table into a JSON-formatted entity collection consumable directly by a 4D Mobile (Wakanda-based) client app, but only supports one selection from one table at a time. The note explains the command's underlying behavior, including the fact that the returned selection is read-only on the client, then presents a custom implementation for returning richer, developer-defined JSON payloads: multiple table selections bundled together, plus arbitrary user data alongside the record selections. It walks through retrieving a selection via the Selected record number command, processing and applying that selection on the 4D Mobile/Wakanda side, building a 4D method that returns multiple named selections on demand, and finally including custom user data fields inside the custom selection JSON structure. This note sits squarely within 4D's short-lived "4D Mobile" product line (built on the Wakanda-derived client technology) introduced around 2015-2016 for building native iOS/Android front ends against a 4D backend. 4D Mobile as a distinct native-app technology was subsequently discontinued in favor of general-purpose REST/ORDA-based web and mobile development (and later Qodly), meaning both the specific commands referenced (Mobile Return selection) and the entire underlying client framework (Wakanda-based 4D Mobile) are now legacy/obsolete from 4D's current product perspective, even though the general JSON-selection-shaping idea remains conceptually sound for any REST API design.
