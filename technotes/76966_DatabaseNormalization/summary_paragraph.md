This Tech Note by Timothy Tse steps back from 4D-specific feature coverage to teach a foundational relational-database design concept: normalization, the set of rules aimed at producing a more efficient, flexible, and maintainable database schema. It opens by weighing the trade-offs — normalization eliminates redundant data, ensures data dependencies, and creates a more flexible, maintainable model, at the cost of making some form displays harder to build and requiring more upfront design work — before introducing the two building blocks every relational design depends on: primary keys (unique, unchanging, non-null row identifiers) and 4D's one-to-many relationships between parent and child tables. It then walks through the first three normal forms in succession: 1NF (eliminate repeating groups by giving related data its own table), 2NF (ensure every non-key column depends on the whole primary key, not just part of it), and 3NF (eliminate transitive dependencies, where one non-key column depends on another non-key column rather than directly on the key). A concrete worked example takes an un-normalized Students table containing Degree, Major, Address, City, and State fields all in one row and incrementally splits it into a properly normalized multi-table design across 1NF, 2NF, and 3NF, quantifying the redundant data eliminated at each stage. The note closes by acknowledging that normalization isn't always the right call for small or stable applications, recommending developers normalize first and then selectively de-normalize only where warranted.
