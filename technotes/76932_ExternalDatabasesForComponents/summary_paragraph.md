This Tech Note by Milan Adamov addresses a design dilemma familiar to 4D component authors: a component sometimes needs its own private data for lookups or internal bookkeeping, but creating tables directly in the host database is considered bad practice since that data is never meant to be shared with or visible to the host. The capability that solves this, 4D External Databases (available since v11), lets a component maintain a completely separate .4DB/.4DD data file of its own — but building and populating that external database purely through SQL commands (`CREATE DATABASE`/`USE DATABASE` with a `DATAFILE` clause) is tedious compared to visually designing a relational structure in 4D's own structure editor. The note's solution is a code library (`MakeSQL_Library.4dbase`) that lets a developer design the component's private structure visually as an ordinary 4D database, then generate a SQL dump of that structure (and optionally its data) via `SQL EXPORT DATABASE`, producing both the SQL script and the initialization method the component will run (`MyComponent_Init`) to recreate the structure and reload the data into its own external database file at runtime — after which the developer deletes the original tables from the working database and installs it as a component in the Components folder of a host database. The note closes by covering the Client/Server case: using `USE REMOTE DATABASE DATAFILE` so all connected 4D Clients share a single external database centrally hosted on the 4D Server machine, rather than each maintaining a separate local copy.
