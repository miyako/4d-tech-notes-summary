Written by Simon J Wright of Knowledge Sharing Systems, Inc., this second of two Tech Notes goes deeper into the design and trade-offs of the Replicator code library, a third-party add-on that replicates data changes between 4D Server installations using the 4D Open for 4D plug-in for cross-database connectivity. It opens by justifying why replication is needed at all (WAN performance, security-driven data subsets, load spreading, merging multiple locations' data, illustrated with a fictional North/South Carolina scenario), then surveys 4D Open's capabilities (multiple simultaneous server connections, cross-platform, record/array/variable binding) and limitations (no subtable support, no built-in locked-record indication, per-connection license consumption). The architectural core covers push-versus-pull replication (Replicator pushes, tracking changes in an `rpl_Queue` table), the ownership problem of avoiding duplicate keys across independently-operated servers (solved via site-prefixed alpha keys), and why database triggers are the right place to capture changes (via `Database Events`) but the wrong place to transmit them (since a slow remote connection would stall the entire server), leading to a queue-based, near-real-time design instead of an unrealistic real-time one. It explains the "most recent" collision-resolution rule Replicator uses when the same record is modified on two servers within the replication delay, and how a dedicated Replication user group lets trigger code distinguish local edits from incoming replicated changes to avoid "replication ping-pong" in two-way or peer topologies. The note closes with a tour of the library's two tables (`rpl_Configuration`, `rpl_Queue`), its key forms (Configuration_dlog, Monitor_dlog), and its principal project methods (`rpl_Initialize`, `rpl_Trigger`, `rpl_ReplicationService`, `rpl_RS_Replicate`, `rpl_RS_ReplicateToServer`), plus practical tuning notes on cycle delay, running the replication client alongside 4D Server, and extending error notifications.
