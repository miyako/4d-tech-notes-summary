This Tech Note by Xiang Liu addresses a fundamental limitation of the original 4D Mobile architecture: because the 4D Mobile API is fully RESTful and all data travels as JSON text, binary content such as images or generated PDFs cannot be transmitted directly through a 4D method call and must instead be encoded into text. The note walks through Base64 as the standard binary-to-text scheme (originating from MIME email attachments) and explains why it's a good fit — printable ASCII, broad cross-platform/cross-language support, and native built-in commands (4D's BASE64 ENCODE/BASE64 DECODE, JavaScript's btoa()/atob() in the browser and Wakanda server). Worked examples cover the two main real-world directions: server-to-client, where a 4D method encodes an image as Base64 and the client decodes it either directly in an HTML element or by writing it to a downloadable file in Wakanda's server-side JavaScript, and client-to-server, where an uploaded image is Base64-encoded on the client (or via Wakanda) and sent to a 4D method that decodes it back into a picture/blob. All demos are built specifically against Wakanda Enterprise 10 paired with 4D v14 R5, reflecting the specific technology stack 4D Mobile depended on at the time — a JavaScript-based Wakanda front-end/server communicating over REST/JSON with a 4D back-end. The note closes by reiterating that Base64 is the practical bridge enabling binary data exchange across this then-new, JSON-only 4D Mobile channel.
