This tech note introduces `Get call chain`, a diagnostic command new in 4D v18 (first available in v17R6), which returns a collection of objects describing every step of the current call stack — mirroring the information shown in the Debugger's Call Chain area but accessible programmatically from any 4D environment, including compiled mode (with Range Checking enabled). Each entry in the returned collection exposes `database` (the database/component that made the call), `line` (call site line number), `name` (method name), and `type` (one of `projectMethod`, `formObjectMethod`, `databaseMethod`, `triggerMethod`, `executeOnServer`, or `executeFormula`), read bottom-up from oldest to most recent call. The note's centerpiece is a sample error handler that combines `Get call chain` with `GET LAST ERROR STACK` (capturing the full chain of underlying errors, useful when one root cause like a full disk cascades into multiple reported errors) and the standard error-context variables (`Error`, `Error method`, `Error line`, `Error formula`), assembling everything — plus a timestamp, 4D and OS usernames, and machine name — into a single JSON object written to a log file under the database's `LOGS/errors` folder, while presenting the end user only a minimal alert referencing the log file path. A companion sample UI, the Error Log Parser, lets developers browse and inspect these JSON error logs, displaying the call chain and error stack in dedicated list boxes for a given selected log file. The note suggests further extensions like replacing the alert with a branded UI or periodically shipping accumulated logs off-device via SMTP/FTP/HTTP, while cautioning that trying to transmit logs at the exact moment of failure can itself fail if connectivity was the problem.
