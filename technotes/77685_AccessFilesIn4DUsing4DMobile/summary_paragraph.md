Written by Xiang Liu of 4D Inc. in November 2016 for 4D Mobile v15.3, this tech note addresses a practical friction point in the 4D Mobile/Wakanda stack: 4D BLOB fields and disk documents can be exposed to a 4D Mobile web client, but JavaScript's BLOB implementation differs from 4D's, so raw BLOB objects returned by Wakanda need to be converted into proper File objects before a browser can use them meaningfully (e.g., as a downloadable file). The note introduces the Wakanda File API, which complies with the W3C File API specification for HTML5, and explains that a File object inherits from Blob (gaining size/MIME-type properties and copyTo/slice/toBuffer/toString methods) while adding richer file-system operations like save, move, rename, and remove, tied to a real path on disk. It walks through accessing files stored in a 4D BLOB field from Wakanda server-side code, converting those BLOBs into File objects with copyTo(), and making the resulting files available to the web client; it also covers accessing files stored directly on the 4D server's disk (outside the database) by retrieving and Base64-encoding them in 4D methods, then decoding and reconstructing the file object on the Wakanda server side before finally decoding and downloading the file in client-side JavaScript. This is a fairly deep, code-level integration guide bridging 4D's data storage model with a JavaScript-facing web runtime. Because 4D Mobile and its underlying Wakanda server were subsequently discontinued in favor of ORDA-based REST APIs and, later, Qodly, the entire Wakanda File/BLOB JavaScript API described here no longer exists in current 4D — making this note a historical record of a defunct integration layer rather than an actionable guide for present-day 4D web development.
