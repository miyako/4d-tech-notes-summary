This Tech Note by David Adams tackles a debugging pain point in 4th Dimension's DOM (Document Object Model) XML commands: internally, an XML document being built is represented as a tree of linked nodes that is invisible to the developer until explicitly converted ("serialized") into text, making it hard to see what's actually happening inside code that constructs XML, including auto-generated SOAP proxy code from the 4D 2004 Web Service Wizard. The note first walks through simple example code using `DOM Create XML Ref`, `DOM Create XML element`, and `DOM SET XML ELEMENT VALUE` to build a small `<contact>` XML document, then contrasts it with denser SOAP-proxy-style code the Web Service Wizard generates, to illustrate why visibility into the tree matters. It introduces the `DOM EXPORT TO VAR` and `DOM EXPORT TO FILE` commands as the mechanism for serializing an XML tree into text (or a BLOB) for inspection, and builds a small custom utility, `DOM_DumpTreeToClipboard`, that calls `DOM EXPORT TO VAR` at each step of tree construction and appends the result plus a diagnostic label to the system clipboard, letting a developer literally watch the XML document take shape command-by-command. Full code for `DOM_DumpTreeToClipboard` is listed, along with a full trace showing the tree's XML output growing from an empty `<contact/>` root through nested `<business>`/`<home>` phone elements. A special section addresses a subtlety around `SET WEB SERVICE OPTION` with the SOAP Header option: because DOM EXPORT commands always produce a fully legal, complete XML document (including an XML prolog), while `SET WEB SERVICE OPTION` inserts the tree's content into a SOAP header without adding a second (illegal) prolog, developers should not be alarmed by an apparently redundant prolog when dumping a tree destined for use as a SOAP header — the discrepancy is only in the debug dump, not the actual SOAP message. Concrete SOAP request XML (with and without a custom credentials header) is shown to clarify this point. The note concludes that dumping XML trees is a fast, general-purpose way to debug DOM-based XML/SOAP construction code and to learn how individual DOM commands affect the underlying tree, and encourages readers to adapt the sample utility for their own use.
