Thang Nguyen, a Technical Support Engineer at 4D, walks through four escalating techniques for recovering a corrupted 4D data file, stressing upfront that 4D's own Backup-plus-log-file integration should always be tried first and that these are diagnostic last resorts requiring a backup before use. The primary tool is 4D Tools, whose Maintain tab offers Check All / Check Records / Check Indexes to detect problems (with Check All recommended for regular maintenance) and whose Repair tab offers matching Repair All / Repair Records / Repair Indexes options scoped to just the damaged portion for efficiency on large databases. When the address table itself is too damaged for standard repair, Nguyen describes Recover by Tags, which rebuilds an entirely new data file from the tag markers stored in each record's header rather than repairing the existing file in place, and flags the need for adequate free disk space and matching multi-segment data file setup. A separate manual re-indexing technique is offered for cases where 4D Tools reports the database as clean yet it still crashes on certain queries: duplicating the structure file, dropping all relations and indexes, relaunching against the original data file to force a re-index, then relaunching the original structure file. The note includes full 4D source for a 'Massaging' method (written by Hugo Fournier) that loops over every table, field, and record, reading and resaving each field's value by type (Alpha, Text, Integer, LongInt, Boolean, Date, Time, Picture, Real, BLOB) to surface which specific record crashes when loaded, logging progress to a 'Record Logs' document next to the structure file. As a true last resort for severely damaged files, the note recommends 4D's built-in Export feature (choosing tab-delimited text or XML rather than SEND RECORD/RECEIVE RECORD, which would re-import the same corruption) since exporting converts each field's value to text and can eliminate corruption that survives a whole-record binary copy.
