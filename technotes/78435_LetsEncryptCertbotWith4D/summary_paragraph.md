This tech note responds to a breaking change: the ACME (Automated Certificate Management Environment) protocol used to talk to the Let's Encrypt Certificate Authority had been updated, meaning the custom 4D component bundled with earlier tech notes 16-17 and 17-01 would soon stop working, and any patched version would face the same fate as the protocol kept evolving. Instead of maintaining a bespoke 4D component indefinitely, the note recommends switching to Certbot, the official client application maintained directly by Let's Encrypt and the Electronic Frontier Foundation, which guarantees ongoing compatibility with protocol changes. It walks through platform-specific installation: on macOS via the Homebrew package manager (`brew install letsencrypt`, `brew upgrade certbot`), and on Windows 10 via the Windows Subsystem for Linux running Ubuntu (since Certbot targets Unix-like systems). Once installed, usage is identical across platforms: running `certbot certonly` interactively prompts for contact email, EFF newsletter opt-in, domain name(s), and — critically for the 4D use case — the webroot folder path corresponding to the 4D Web Server's WebFolder, which Certbot uses to serve the ACME HTTP-01 challenge file. Upon success, Certbot writes `fullchain.pem` and `privkey.pem` under `/etc/letsencrypt/live/<domain>/`, which must then be copied (renamed `cert.pem` and `key.pem`) into the 4D database's folder, followed by a `WEB SERVER STOP`/`WEB SERVER START` cycle to load the new certificate. The note also covers renewing certificates with `certbot renew` and building a renewal script, plus common pitfalls around webroot path errors and web server startup failures. This represents 4D moving from an internally-maintained TLS helper to relying on the broader Let's Encrypt ecosystem's own tooling for long-term sustainability.
