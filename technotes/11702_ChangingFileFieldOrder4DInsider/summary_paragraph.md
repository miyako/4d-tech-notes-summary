This Tech Note explains how to change the order of fields or files in a 4D database structure during development, using 4D Insider to avoid corrupting existing layouts and procedures. It begins by explaining the core problem: fields referenced in layouts and procedures are tokenized by position, not name, so simply reordering fields or adding new ones in the Structure window silently changes the logical meaning of every layout and procedure that references those fields — a highly undesirable side effect. The documented workaround exploits 4D Insider's ability to move objects between databases, which retokenizes references by name rather than position. For field order changes, the procedure involves duplicating the database, making the desired field edits in the copy, quitting 4D, then using 4D Insider to Control-drag the affected procedures and layouts from the original database into the modified copy, choosing "Replace" so Insider detects structural differences and retokenizes accordingly. A parallel but distinct procedure is given for changing file order: because every new structure has a first file already created (often used as an invisible dialogs file), the developer must create a new database, address the first file's fields appropriately, then Control-drag files one at a time (without their associated procedures/layouts) into the desired order, followed by dragging all remaining non-file objects over in a final step. The note stresses backing up the project before either operation and notes that any existing data will still need to be migrated via 4D's Import and Export editors. The featured technology throughout is 4D Insider as a structure-editing companion tool, working against 4D's classic tokenized, position-based binary structure format. As a purely developer-facing, structure-maintenance-oriented note, it targets the practical realities of maintaining generic, well-ordered databases during active development in the 4D v3.x era.
