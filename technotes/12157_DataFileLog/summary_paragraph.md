This Tech Note by Steve Hussey (CEO, Alto Stratus LLC) addresses a practical concern for 4D developers of the era: a 4D data file could comprise up to sixty-four 2 GB segments, and if the first segment filled before additional segments were created, remote clients could run into serious, time-consuming problems -- yet it was hard to know when a client's data was approaching that limit or how fragmented (percentage of deleted records) their tables had become. The example database's "Create Log File" menu item calls the `LOG_Create` project method, which prompts for a save location with `Create document`, writes a tab-delimited header, then loops through every data segment returned by `DATA SEGMENT LIST` writing each segment's size (via `Get document size`) and full path with `SEND PACKET`. It then loops through every table using `Count tables`, computing record counts with `Records in table`, deletions by subtracting current records from `Sequence number` minus one, and a fragmentation percentage from the deletions-to-records ratio, writing it all as a tab-delimited row openable in any spreadsheet like Excel. The note explains that `LOG_Create` is fully structure-independent and portable to any database, but on 4D Server it must run inside a Stored Procedure rather than on 4D Client, because of how `DATA SEGMENT LIST` behaves, and suggests scheduling it periodically (e.g. weekly) with results e-mailed via 4D Internet Commands to proactively warn about new segments needed or excessive fragmentation.
