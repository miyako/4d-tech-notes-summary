This Tech Note by David Adams addresses a usability shortcoming in 4th Dimension 2004's built-in HTTP password support, implemented through the On Web Authentication database method: when a user's password dialog is cancelled, the 4D Web server simply returns a blank page, which confuses end users into thinking the site has disappeared, rather than a helpful custom error page. The note carefully walks through the real mechanics of HTTP Basic Authentication — the browser (not the server) draws the password dialog, the server first responds with an HTTP 401 status and a WWW-Authenticate header, and if the user cancels the dialog, the browser displays whatever error page content the server originally sent with that 401 response — and shows that 4D's On Web Authentication method always returns an empty 401 response with no page content, which is the true source of the blank-screen problem and cannot be fixed by adding code inside On Web Authentication itself. Its proposed solution is to accept all requests unconditionally within On Web Authentication (deferring actual authentication) and instead perform login checks manually in On Web Connection and in any method invoked directly via 4DACTION, since 4DACTION calls bypass On Web Connection entirely. Two accompanying sample databases are provided: Web_Login_Default, illustrating the default blank-screen behavior, and Web_Login_Custom, implementing the full custom challenge/response solution with a proper HTML error page shown when login is cancelled. The note documents the exact HTTP response headers 4D sends (including the `WWW-Authenticate: Basic realm=...` header) and walks through building a manual 401 response with attached content. It closes with several important caveats: HTTP Basic Authentication is fundamentally insecure (credentials are only base64-encoded, not encrypted, so SSL/HTTPS is required for real security); the "Include 4D Passwords" web preference should never be enabled in a mixed Web/4D Client environment since it exposes real 4D user credentials over an insecure channel; browsers cache and resend credentials for the life of the browser session, complicating testing; and case-sensitivity of user names/passwords is a project-specific decision (with a pointer to a related Tech Note on case-sensitive string comparisons).
