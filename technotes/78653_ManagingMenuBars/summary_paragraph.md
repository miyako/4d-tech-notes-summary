This tech note addresses a common desktop-application UI challenge in 4D: keeping menu bar item states (enabled/disabled, added/removed) correctly synchronized as a user navigates between forms and processes, using a mail client (compose vs. inbox) as the motivating example. It contrasts three ways to assign a menu bar — associating a Toolbox menu bar via the form's property list, assigning one programmatically by number with SET MENU BAR, and creating an independent runtime instance with Create menu — and explains that the first two approaches share state globally across every form/process using that same Toolbox menu bar, which becomes a problem when different forms need different menu states simultaneously. The recommended technique is to create a distinct menu bar reference per form via Create menu, assign it with SET MENU BAR in each form's On Load event, mutate its state with commands like DISABLE MENU ITEM, and explicitly reassign the previous form's reference (e.g. after a DIALOG or CLOSE WINDOW call) when returning to it so its remembered state is restored; RELEASE MENU must be called in On Unload to free each reference from memory. Three demos build up the pattern: independent states across two forms in the same process, keeping UI buttons in sync with menu item states driven by user list box selections (using SET MENU ITEM PARAMETER to differentiate shared generic menu handler logic per form), and managing menu bars across forms opened in separate processes (New process/Open form window), where menu item properties (SET/GET MENU ITEM PROPERTY) let one process communicate flags like "record was saved" back to another process's referenced menu bar without needing manual reassignment, since each process already owns its own menu bar context.
