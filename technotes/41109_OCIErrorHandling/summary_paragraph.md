This Technical Note by Josh Fletcher explains the two error-handling techniques available when using the 4D for OCI plug-in, which lets 4D applications connect natively to Oracle servers via the Oracle Call Interface (OCI). "Standard error handling" requires the developer to manually check the return code of every 4D for OCI function call (values like OCI_SUCCESS, OCI_ERROR, OCI_INVALID_HANDLE, OCI_NEED_DATA, and others, drawn from Oracle's own OCI Programmer's Guide) and branch into custom error-handling code as needed, giving full control at the cost of more repetitive code. "4D error handling," by contrast, uses the OCIOnErrCall command to install a project method as a centralized error-catching handler — conceptually similar to 4D's own ON ERR CALL — so that any OCI error automatically triggers the handler without extra per-call checking, trading some control for much less code. The note explains that OCI programming further depends on error handles, which reference one or more error records containing an Oracle error code and message text, retrieved via the OCIErrorGet command by looping until OCI_NO_DATA is returned. It presents a complete, reusable custom error handler (My_OCI_Error_Handler) that works with either technique and displays formatted alert messages for each OCI return code. The accompanying sample database includes a test dialog for running a deliberately malformed SQL statement and a valid one against a real Oracle connection, toggling between the two error-handling styles, plus example project methods (Query_Using_Standard and Query_Using_OCIOnErrCall) illustrating each approach in practice.
