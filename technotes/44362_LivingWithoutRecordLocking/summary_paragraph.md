This Tech Note by David Adams tackles a subtle architectural issue: 4th Dimension and 4D Client/Server automatically manage record locking at the database engine level for standard multi-user/multi-process access, but this automatic protection silently fails to apply in several common scenarios — Web- and SOAP-based record modification, array/variable-based systems (4D, 4D Client, or 4D Open interfaces using AreaList, 4D View, or list boxes that work with copies of field values), and file-based systems combining or importing records from remote sources. The note explains the underlying reason: 4D's automatic locking depends on records being held open within the context of a specific, ongoing 4D process, but Web and SOAP requests are stateless, so once a request completes there is no process left to hold a lock, and no amount of custom process management can safely emulate an indefinite lock duration (since there's no correct answer to "how long should a record stay artificially locked?"). Rather than trying to build a custom locking system, the note walks through a worked example — an address record simultaneously edited by a warehouse worker (via Web) and a traveling sales rep (via SOAP) — to demonstrate that what's actually needed is much simpler: detecting whether an incoming update is based on a stale copy of the record. It proposes maintaining a simple integer "update/version number" field on each table, incremented every time the record is saved, most robustly enforced inside a trigger keyed on `On Saving New Record Event` and `On Saving Existing Record Event`; the trigger compares the incoming record's version number against the current (`Old(...)`) value and rejects the save with a custom trigger error code if they don't match, indicating the incoming data is out of date. Concrete 4D trigger code is provided for both initializing the version number on new records and validating/incrementing it on updates. The note also briefly discusses alternatives to a simple integer counter (e.g., date-time stamps) and offers a sidebar of tips for developers who insist on attempting a custom process-based locking system anyway (e.g., using `PUSH RECORD` or transaction-held locks). It concludes that this optimistic-concurrency approach, requiring only a maintained and tested version counter, correctly and simply handles record-conflict scenarios of arbitrary complexity regardless of how or where updates originate (Web, SOAP, import, or standard 4D forms).
