This Tech Note, authored by 4D S.A., is a deep dive into how 4th Dimension's in-memory cache works and what specifically changed and improved in version 2004's cache and memory management. It opens with background on OS-level virtual memory and disk caching (how Windows 2000/XP and Mac OS X allocate RAM, page to disk when physical memory runs low, and maintain their own disk caches), before explaining that 4D builds its own cache on top of this to store address allocation tables, index pages, and records, giving 4D fine-grained control over what stays in memory and for how long. It describes 4D's priority-based object eviction (objects with lower priority — typically records — are unloaded first when cache space runs low, followed by index pages, then address tables only in extreme cases) and explains the "flushing" operation (writing dirty cache contents to disk), which can be triggered automatically on an interval (recommended 5–30 minutes), via the FLUSH BUFFER command, or manually via the User environment menu, primarily to protect against crashes/power loss. The note then walks through general guidance for optimal cache sizing: address/allocation tables and index pages should generally always be cached (since almost every operation depends on them), while whether records benefit from caching depends on whether they are reused (repeatedly accessed data benefits strongly; data used only once does not, and an undersized cache under heavy reuse can cause thrashing that is worse than no cache at all); transactions and selections also consume cache space and should be accounted for when sizing. It then details three specific improvements shipped in 4D 2004: (1) elimination of cache fragmentation issues at large cache sizes (previously a problem, now resolved even at sizes up to 1 Gb), (2) an optimized cache-flush write algorithm that reduces redundant disk writes (making the older 4D 2003 SET DATABASE PARAMETER selector-26 "optimize cache writing" option largely obsolete, and even potentially detrimental except on highly fragmented data), with benchmark figures showing flush throughput improving from roughly 10-15 Mb/s to 40-45 Mb/s on a PowerMac G5, and (3) faster record loading (up to 50% faster on higher-end machines) by taking advantage of the OS-level system cache, requiring no code changes. Finally, the note walks through using 4D's Runtime Explorer to check cache statistics (index page hit ratio near 100%, record hit ratio, transaction/selection hit ratios) and recommends flushing the cache after bulk operations like deleting over 100,000 records or large transactions to reclaim space used by record markers. It closes by reminding developers that overall database performance is ultimately bounded by available OS-level RAM and that cache tuning is a database-by-database exercise best validated with real testing.
