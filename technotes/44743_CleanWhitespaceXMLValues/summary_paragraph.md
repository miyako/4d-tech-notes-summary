This Tech Note by David Adams explains why XML element values read through 4th Dimension's DOM and SAX commands (such as DOM GET XML ELEMENT VALUE and SAX GET XML ELEMENT VALUE) often include unexpected leading or trailing whitespace, since the XML specification legitimately treats tabs, line feeds, carriage returns, and spaces around an element's text content as part of its value. It walks through a concrete example — a `<business>` element whose apparent text value "ACME Black Dot" actually includes surrounding whitespace characters used purely for readability in the source XML — to show how naive value reading can produce messy results in code. Because 4D's built-in element-reading commands provide no option to trim this whitespace automatically, the note designs and documents a custom trimming function, XML_CleanWhitespace, that solves the problem efficiently. Rather than repeatedly resizing the string character-by-character (which could force 4D to reallocate memory multiple times), the algorithm makes a single pass to find the first non-whitespace character, a second pass from the end to find the last non-whitespace character, and then extracts the substring between them in one operation. An accompanying array-based helper, XML_InitWhitespaceCharacters, initializes an interprocess array of the four XML whitespace characters (tab, line feed, carriage return, space) so the trimming logic can test characters generically via Find in array rather than hard-coded comparisons. The note explains that this array-driven design is intentionally more flexible than hard-coded character checks, since developers can extend or change what counts as "whitespace" (e.g., adding other control characters) by editing the array's contents rather than rewriting the trimming method's logic. A full 4D code listing of both the initialization array and the XML_CleanWhitespace function is provided, along with a discussion of edge cases (fully-whitespace or empty strings). The technical note is accompanied by a sample database implementing the function for direct reuse. It closes by reiterating that this missing trimming capability is easy to add given 4D's native string commands (Substring, Find in array), and that the featured implementation is a reusable, efficient pattern applicable beyond just XML value cleanup.
