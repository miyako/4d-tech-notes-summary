This Tech Note explains 4D's preemptive multitasking model and, specifically, the v17R4 milestone of extending preemptive execution to 4D Remote (client) processes, not just 4D Server/standalone. It first distinguishes cooperative mode — where processes share a single CPU by yielding control (explicitly via IDLE or implicitly through most language commands) — from preemptive mode, where the OS itself schedules threads across multiple cores for true parallelism, at the cost of requiring every command in the call chain to be thread-safe. Three requirements are laid out for any preemptive process: the 64-bit version of 4D/4D Server must be used (32-bit is incompatible), the code must run in Compiled context (merged apps, compiled 4DC structures, or interpreted 4DB running compiled), and every command/method in the call chain must be explicitly marked "can be run in preemptive processes" and pass compiler thread-safety checks — checkable either via the green "preemptive mode" icon in command documentation or via compile-time errors that name the first non-thread-safe command encountered (e.g., SET TEXT TO PASTEBOARD). For 4D Remote specifically, v17R4+ is required along with the New Network Layer (the legacy layer disables preemptive execution for clients). When a non-thread-safe command can't simply be removed, the note offers two refactoring paths: spinning off an asynchronous cooperative task via New process when no result/wait is needed, or using the newer Signal object (New signal, signal.wait(), signal.trigger(), signal.signaled) to let a preemptive process synchronously pause for a cooperative task's completion. PROCESS PROPERTIES is shown as the way to programmatically check whether the current process is running preemptively or cooperatively, complementing icon-based indicators in the Runtime Explorer and 4D Server admin window.
