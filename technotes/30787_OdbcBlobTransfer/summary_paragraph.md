Written by Jamras Komoncharoensiri (Technical Support Engineer, 4D, Inc.) as Technical Note 03-52, this note addresses a specific, practical problem: how to correctly move picture and plug-in document data between a 4D database and an ODBC-connected SQL Server (via the 4D ODBC plug-in) while preserving the data's original type when it comes back out. It works through three scenarios using `OC Create cursor`, `OC Set SQL in Cursor`, `OC Bind parameter`/`OC Bind`, `OC Execute cursor`, and `OC Load row`/`OC DROP CURSOR` as the common ODBC plumbing. In Scenario 1, a true picture field is sent by first converting it with `PICTURE TO BLOB([PictureLibrary]Picture;vBlob;"JPEG")` before binding the resulting blob parameter, and retrieved by loading the blob and converting back with `BLOB TO PICTURE`, since simply passing the raw picture field would not preserve its picture-type fidelity. Scenario 2 covers the trickier case of a 4D Write plug-in document stored inside a picture field: sending it requires first restoring the document into a 4D Write offscreen area (`WR New offscreen area`, `WR PICTURE TO AREA`) and converting it with `WR Area to blob` before it can go into the BLOB parameter, while retrieving it requires the reverse — `WR BLOB TO AREA` followed by `WR Area to picture` — to restore the document's proper 4D Write properties before saving it back into a picture field. Scenario 3 shows the simplest case: a plug-in document already stored natively in a BLOB field can be transferred with no conversion at all, since the blob already holds a valid document. The note closes by noting this approach generalizes to any data type that can be represented in a blob, not just pictures and 4D Write documents.
