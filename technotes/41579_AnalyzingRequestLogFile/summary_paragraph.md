This Tech Note is a direct continuation of TN 06-03 ("Recording Information sent Between 4D Client and 4D Server") and uses the same request-log-file technique to compare, request by request, the network cost of common 4D Client/Server programming patterns, since network latency and request volume are frequently the limiting factor on client performance. Example 1 compares three ways to browse a selection — a While/End selection loop with NEXT RECORD, a For loop with NEXT RECORD, and a For loop with GOTO SELECTED RECORD — showing the first two are request-equivalent while GOTO SELECTED RECORD generates two extra requests because ALL RECORDS already loads the first record. Example 3 shows the request pattern (Rec_load/Rec_Save/Rec_Unload cycles) generated when batch-modifying and saving 8 records in a loop. Later examples (referenced in the note's structure, examples 4 through 8) cover transactions, sorting a selection, searching a selection, transferring inter-process array variables between 4D Client and 4D Server via GET PROCESS VARIABLE (noting that string arrays consume noticeably more bytes over the network than text arrays, relevant when passing data via BLOBs to stored procedures), and a semaphore-based synchronization pattern using Execute on server, DELAY PROCESS, and a busy-wait IDLE loop polling Test semaphore, illustrated with a very long, granular request log showing thousands of near-instant Sem_Set-style polling requests. Throughout, the note treats the request log as a black-box performance-profiling tool: rather than guessing at what the 4D runtime does internally, developers can directly observe which language commands generate which server requests, how many bytes are transferred, and how long each takes, enabling data-driven choices between functionally equivalent coding patterns in Client/Server 4D applications.
