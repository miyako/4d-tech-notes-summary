Written by Erick Lui, this Tech Note explains the two record-conflict-prevention mechanisms available to 4D developers as of v17: classic 4D pessimistic record locking, and the newly introduced ORDA entity locking, which supports both optimistic and pessimistic modes. In classic 4D, each table per process is either read-only or read/write (set via commands such as `READ ONLY`/`READ WRITE`), and loading a record with commands like `QUERY` or `NEXT RECORD` locks it for exclusive read/write access until `UNLOAD RECORD` is called; the note tabulates the resulting record states and shows how `Locked`, `LOCKED BY`, and `Get locked records info` let a process check lock status and identify the blocking user/process, illustrated with a `READ WRITE`/`MODIFY RECORD`/`UNLOAD RECORD`/`READ ONLY` code pattern and listbox screenshots of two competing processes. It then pivots to ORDA, explaining that entities carry a "stamp" used to detect concurrent modification, and walks through three concrete scenarios: pessimistic locking via `entity.lock()`/`entity.unlock()`; optimistic locking via a plain `entity.save()` call that fails if the stamp has changed since load; and optimistic locking with automatic conflict resolution using `entity.save(dk auto merge)`, which merges non-conflicting field changes rather than rejecting the save outright. The note frames pessimistic locking as best suited to high-conflict-probability records and optimistic/stamp-based locking (the ORDA default) as better for low-conflict scenarios with many concurrent users, leaving the choice up to the developer's use case. This positions the note as an essential bridge document for 4D v17 developers adopting ORDA while still maintaining classic 4D data-access code, clarifying how the two locking paradigms coexist and differ.
