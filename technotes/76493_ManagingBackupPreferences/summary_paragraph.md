This Technical Note by Charles "Charlie" Vass tackles an often-overlooked step in deploying distributed 4D applications: managing the Backup.XML preference file that 4D creates and maintains relative to the structure file's location. The note describes a typical scenario where a developer tests backup successfully during development, only to discover that when the application is built as a merged/server application for delivery — especially with the data file stored separately from the structure — necessary preference files scattered under the "Preferences" folder don't automatically carry over, and simply copying the whole folder risks including unwanted build artifacts like the XML project file. To solve this, the note shows three approaches to Backup.XML management: copying and restoring an existing Backup.XML file, programmatically building a new Backup.XML file from scratch, and an alternative "Backup.XML2" concept, each suited to different deployment situations (initial launch configuration, preserving prior settings, or accompanying the app at distribution). A substantial included component, BKP_Manager, automates the most sophisticated of these tasks and is demonstrated via a full demo database (with separate Data and Structure folders) plus a client/server interaction walkthrough, an "Advance Settings" configuration dialog, and processing logic for applying the chosen settings. The note is written to be compiler-friendly, showing how a host application can optionally include the BKP_Manager component without hard dependencies, making it easy to adopt selectively across different distributed applications.
