This Tech Note by Milan Adamov solves a narrow but painful legacy-migration problem: in 4D version 2004 and earlier, it was possible to create a subtable containing fields related to a field in another table, using nested `RELATE ONE` calls (first loading the parent record's relation, then the subtable's). When such a structure is converted to 4D v11 SQL or later, subtables are automatically converted into regular standard tables (with a new field added to preserve the parent link), but the relation itself is dropped from the converted structure entirely — silently breaking any code that depended on it. The note explains the underlying mechanics of the problem in detail, translating the old `RELATE ONE`/`RELATE ONE` chain into its logical equivalent (`QUERY` followed by `QUERY SUBRECORDS`) to make clear exactly what functionality is lost, then walks through the fix: exporting relation metadata from the 4D version 2004 structure into a tab-delimited text file (table/field names on both sides of the relation), reading that file into 4D arrays after conversion, and then looping over every project method in the converted database, using `Replace string` to substitute the old subtable-relation code pattern with its v11+ equivalent (a `QUERY` on the newly-standard-table using `Get subrecord key` to establish the same relationship, followed by the original `QUERY SELECTION`), and finally committing the rewritten method bodies with `METHOD SET CODE`. The note acknowledges subtables had long been discouraged, but notes many developers nonetheless kept creating them, making this migration path a necessary tool for teams bringing legacy 4D 2004-era applications forward to v13.
