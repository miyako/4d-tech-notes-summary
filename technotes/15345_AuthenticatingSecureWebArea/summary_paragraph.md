This Tech Note by Jonathan Baltazar (4D, Inc.) reviews several approaches to securing a portion of a website served by 4D, using the "Web Exam" example database (which lets enrolled students log in, take an exam, and get a computed grade) as the working illustration. The first approach is a fully custom, application-level login: an HTML login page posts to a `/4DACTION/W_Cert` action, whose `W_cert` method runs a `QUERY([Students];[Students]Name=User)` against a 4D table and routes the browser to the exam (`SEND HTML FILE("test.htm")`), a retry page, or a name-error page depending on whether the credentials match. The second approach uses 4D's built-in Password System: creating non-default users in the Password Editor and enabling "Use Passwords"/"Include 4D Passwords" in the Web Server II database properties triggers 4D's own login dialog, provided no `On Web Authentication` method exists (its presence signals that the developer intends to handle security manually). The third and most flexible approach is the `On Web Authentication` database method, which receives six parameters — URL, the full HTTP header+body, client IP, server IP, username, and password — and must return a Boolean `$0` indicating whether to accept the connection; the note shows example code using `GET USER LIST` and `Is user deleted` to validate 4D users, and a `WithWildcard` helper method to reject wildcard-containing usernames/passwords as a security precaution. It closes by noting which security combinations are compatible with 4D Link/WebSTAR, `nph-cgi4d.exe` (Apache for Windows), and `4DISAPI.dll` (IIS), the last of which requires a fully custom password system since it doesn't forward the $5/$6 username/password parameters.
