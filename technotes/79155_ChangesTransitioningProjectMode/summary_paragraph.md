This Tech Note catalogs seven concrete behavioral differences that developers must manually inspect and fix when converting a binary 4D database (.4DB) into a project database, since 4D automates most of the conversion but leaves some code-logic gaps. Using a paired demo pair (demoBin.4dbase vs. demoProj), it shows that in project mode's standalone/single-user mode the current user is always forced to "Designer" and `CHANGE CURRENT USER` has no effect (client-server mode is unaffected), that `USERS TO BLOB` returns an empty blob so custom login systems must instead read the new `directory.json` settings file via `Document to text` + `JSON Parse`, and that the classic Picture Library is no longer used — pictures are stored on disk in the Resources folder, so `READ PICTURE FROM LIBRARY` must be replaced with `READ PICTURE FILE`. It also covers the removal of the picture "Transparent" toggle property (superseded by native PNG alpha-channel support, with `TRANSFORM PICTURE` as a workaround), the replacement of the legacy "Radio buttons grouped by name" compatibility setting with an explicit "Radio Group" property, and the automatic conversion of Highlight buttons into plain regular buttons that lose their enabled/disabled/clicked visual states — for which the note supplies a full utility method that parses the project's conversion log JSON, generates a 2-state SVG image via the SVG_ toolbox, and rewrites each affected form's `.4DForm` JSON to apply a custom background picture and click event that emulate the old highlight behavior. Finally, it addresses read/write access to Lists in client-server: 4D 19.x/19R5 4D Remote clients get only read-only access to source code (including lists) since 4D Remote downloads a snapshot .4DZ, while 19R6+ adds development mode for 4D Remote clients enabling write access, with a fallback of moving list data into a table for older versions. The note positions itself as a practical pre-flight checklist to prevent silent UI/logic regressions when adopting project mode.
