This technical note provides a foundational explanation of NULL values in 4D v11 SQL, addressing a critical SQL compatibility feature that distinguishes 4D v11 from earlier versions and from developers unfamiliar with NULL semantics. A NULL is a value that exists but whose content is unknown—distinct from an empty string or zero. The note motivates NULL usage with the example of a youth soccer league where some teams do not report scores; treating unreported scores as NULL (rather than defaulting to zero) ensures that aggregate functions (AVG, SUM, MIN, MAX) compute mathematically correct results: AVG with NULLs counts only reported teams (six), yielding a true average of 19.83, whereas AVG with zero-defaults would incorrectly include unreported teams, yielding 14.875. In 4D v11 SQL, any field in any table can contain a NULL value; developers control NULL behavior via two field properties: (1) "Reject NULL value input" prevents NULL insertion at the database engine level (stronger than "Mandatory" which operates at data entry level only), and (2) "Map NULL values to blank values" converts NULLs to type-specific defaults (empty string for text, 0 for numeric, 00/00/00 for date, etc.). The 4D language provides two commands: `IS FIELD VALUE NULL(field)` returns TRUE if a field contains NULL, and `SET FIELD VALUE NULL(field)` sets a field to NULL. In SQL, the operators `IS NULL` and `IS NOT NULL` query for NULL values, and NULLs are correctly handled by aggregate functions (COUNT, SUM, AVG, MIN, MAX all ignore NULLs in their calculations). Importantly, NULLs in 4D fields display as their default values but remain internally NULL; querying for the default value (e.g., zero) returns no results for a NULL field. This distinction is critical for developers migrating from 4D v10 and earlier.
