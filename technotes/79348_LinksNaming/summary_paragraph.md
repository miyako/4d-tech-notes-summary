This technical note addresses a legacy problem in 4D databases: for years, links between tables were given largely unused default names such as "Lien_55" or "Link_78_retour" (and their language-localized variants), which are harmless in classic 4D code but become a real liability once a database adopts ORDA, since ORDA exposes link attributes directly as entity properties that developers reference by name in code. The note first provides a diagnostic script that walks every dataclass and attribute via `ds`/`For each`, checks whether each relatedEntity attribute's `.name` or `.inverseName` still matches the default patterns ("Link_@", "Lien_@", "Verknüpfung_@"), and reports the ratio of correctly-to-incorrectly named links plus the affected table list to the pasteboard — usable against a v18 database or an express-converted structure copy. It then lays out a concrete nomenclature: tables should be named in the singular with a capital letter (e.g., "Company", since a table represents a record schema, not a collection), fields should be lower-case except primary keys, and — the note's central recommendation — link attribute names should mirror how they're used through entities: the many-to-one (N-1) link should be named singular and lower-case (e.g., an Employee's "company"), while the corresponding one-to-many (1-N) return link should be named plural and lower-case (e.g., a Company's "employees"), explicitly avoiding "Table1_to_TableN"/"TableN_to_Table1" style names because they introduce redundant, verbose code such as `$company.Company_to_Employee` instead of the clean `$company.employees`. For project-mode databases with many tables, the note offers a practical shortcut: directly editing the `name_Nto1` and `name_1toN` attributes inside the `relation` XML elements of the `Project/Sources/catalog.4DCatalog` file and then restarting the project, rather than manually renaming each link through the structure editor. The overarching principle, restated in the conclusion, is that link names should express the conceptual relationship at each end (e.g., "employees" of a company, "company" of an employee) rather than mechanically encoding the field-to-field relationship or table direction.
