This Tech Note introduces two intertwined ideas: the newly available 4D Project Mode and how it enables proper version control with Git and GitHub, something not previously practical with 4D's binary structure files. It explains that starting in v17R5, a classic .4DB binary database can be converted (one-way, via File > Export > Structure to project…) into a "Project" folder containing every database element — forms, methods, menus, catalog/structure — as individual text files (.json, .4dm, .4DCatalog), organized into BuildSettings, DerivedData, Sources, and Trash subfolders, while compilation into a single deployable file remains possible. This text-based, per-file structure is what finally makes a real diff/merge-based Git workflow feasible for 4D projects. The bulk of the note is then a comprehensive, from-scratch Git/GitHub tutorial: distributed vs. centralized VCS concepts, the local working-directory/staging-area/repository architecture, remote repositories, branching model (feature branches diverging from and merging back to master), step-by-step Git installation on Windows and macOS (including the credential helper setup), and creating a first remote repository. Three demos anchor the practical side: interacting with a remote repository (push/pull/reset --hard), conflict management (walking through a real merge conflict and its resolution), and branching/stashing workflows. The note positions Git as a "necessary evil" for any team once a codebase exceeds trivial size, and frames 4D's new Project Mode as the missing piece that finally lets 4D teams adopt standard, industry-wide source control practices.
