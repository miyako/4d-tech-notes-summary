Written by David Adams, this Technical Note explores the range of behaviors 4th Dimension exhibits when a custom method is called with too few parameters, using a trivial DisplaySum example method that adds two longint parameters, and then presents a reusable defensive-coding pattern to prevent the problem entirely. It walks through four distinct scenarios: in interpreted mode, calling the method with a missing parameter reliably produces a clear syntax error dialog; in a compiled database without range checking on Windows, the same bug can cause an outright crash with an unhelpful, uninformative error screen; on OS X under the same compiled-without-range-checking conditions, the result can be even more insidious — silently wrong calculated output with no visible error at all; and with range checking enabled during compilation, 4D again shows a syntax-error-like dialog similar to interpreted mode, which the note recommends always enabling despite negligible runtime cost. Because none of these default behaviors are guaranteed or documented to remain consistent across 4D versions, and because a bad parameter list is fundamentally a developer bug, the note argues it should always be actively detected and handled rather than relied upon. The proposed fix starts with a simple If (Count parameters=...) check wrapped around parameter use paired with an ALERT (noting ALERT is inappropriate in triggers, Web, or SOAP contexts where errors should instead be logged or returned), then generalizes this into a centralized ParameterCountIsOkay(methodName; min; max; count) validator function that any method can call to both validate its own parameter count and produce a clear, consistent error message identifying which method was misused and how many parameters were expected. The note also notes that ON ERR CALL, while useful for other error trapping, does not meaningfully help with bad-parameter-count errors in compiled code. Featured technology/language elements include Count parameters, the ALERT command, custom C_TEXT/C_LONGINT/C_BOOLEAN typed parameter declarations, and the classic 4D compiler's range-checking option, all illustrating a general defensive-programming discipline for validating method inputs before use.
