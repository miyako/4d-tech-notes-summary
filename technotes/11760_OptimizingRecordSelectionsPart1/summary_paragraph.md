This is Part 1 of a two-part Technical Note focused on helping developers optimize the handling of record selections as 4D data files grow larger and as more 4D Client or Web connections are added to a database. Part 1 specifically covers how a 4D data file is organized — how it uses disk space and how it is represented in memory — laying the technical groundwork that Part 2 builds on when discussing current record, current selection, and named selection concepts. The note explicitly states that its content applies equally across Macintosh and Windows platforms, across both single-user 4D and 4D Client/Server configurations, and across both 4D version 3 and version 6, signaling that the underlying data file organization it describes had remained largely stable across that span of releases. This makes the note a foundational, architecture-level companion to the more concept-and-technique-focused Part 2, aimed at developers who want to understand why certain selection-handling techniques improve performance, not just which techniques to apply. As a scalability-focused note, it targets a real and recurring concern for 4D Client/Server deployments as they grew in data volume and simultaneous user count during the mid-to-late 1990s.
