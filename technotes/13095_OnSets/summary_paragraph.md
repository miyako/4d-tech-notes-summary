This Tech Note by Jean-Yves Fock-Hoon (Quality Assurance Manager, 4D, Inc.) explains 4D's Set data structure as a lower-memory, unordered alternative to the ordinary current selection. A selection is a sortable list of pointers requiring four bytes per record and existing only in memory, whereas a set uses just one bit per record to record membership, can be saved to and reloaded from disk, and supports combining two sets via UNION, INTERSECTION, and DIFFERENCE, plus fast membership testing with `Is in set`. The note describes 4D's three set scopes -- inter-process sets (prefixed `<>`), process sets (no prefix), and local sets (prefixed `$`, existing only on the 4D Client machine) -- and explains 4D's two automatically managed sets, "Lockedset" (records locked by other processes during `ARRAY TO SELECTION`/`APPLY TO SELECTION`/`DELETE SELECTION`) and "Userset" (records the user has highlighted in a displayed selection). Using the example database's People table (50,000 RPG-player records), it demonstrates creating named sets from highlighted records and combining them, then walks through benchmark comparisons showing that repeated non-indexed-field queries can take 118-152 ticks versus 0-3 ticks when simulated with a pre-built set and USE SET/INTERSECTION/UNION/DIFFERENCE, and explains why using sets across a Client/Server configuration requires extra bookkeeping methods (`ROBOT_Rec_has_been_Created/Modified/Deleted`) to keep sets in sync as records change.
