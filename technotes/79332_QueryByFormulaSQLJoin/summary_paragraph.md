This technical note walks developers through safely activating the "QUERY BY FORMULA use SQL Join" database compatibility property, a feature available since 4D v11 that changed QUERY BY FORMULA/QUERY SELECTION BY FORMULA from sequential-search commands into commands that can use indexes and resolve ambiguous multi-table relationships as proper joins. The motivating example is a flights/lines/airports schema where a simple `QUERY([Flight];[Airport]IATA_AirportCode="SFO")` cannot resolve which of two possible paths (departure vs. arrival) connects Flight to Airport; `QUERY BY FORMULA` solves this by combining a search criterion with explicit relationship-defining equality expressions (e.g., `([Flight]UUID_Line=[Line]UUID) & ([Line]UUID_Airport_To=[Airport]UUID)`) joined with `&`, letting a single command specify criteria, relations, and conjunctions at once, replacing three round-trips of `QUERY`/`RELATE MANY SELECTION` client-server calls with a single indexed join in one request. Because older databases (pre-v11.2, where the property is now on by default) may have code written against the old sequential-search semantics, the note explains how to audit existing usage with the development search tool (including the wildcard trick to catch both formula commands), and classifies found usages into four cases: pure 4D-function formulas, 4D-method expressions, simple field comparisons (already index-using since v11) — all three unaffected by the property — versus the risky fourth case where a field is used as a static "current record" value in an equality expression, which becomes a relationship-join expression instead once the property is enabled; the fix is to pre-extract that field's current value into a local variable before the query. The note also covers the `SET DATABASE PARAMETER` selector 49 (recommended only for investigation, not production use, in favor of doing the actual code migration), and shows how `DESCRIBE QUERY EXECUTION` combined with `Get last query plan`/`Get last query path` can be used to verify exactly what joins and indexes a formula query is using and how many records were found at each stage. It closes by noting the client-server efficiency win — a single request and a smaller footprint of modified selections/records — as an added incentive to complete the code migration once the compatibility property is safely enabled.
