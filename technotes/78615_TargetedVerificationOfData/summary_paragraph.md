This Tech Note opens by cataloging 4D's built-in ways to verify a data file's health: the Maintenance and Security Center (MSC) Verify tab, usable from both 4D and 4D Server without the database running, and the 4D Server Administration Window's "Verify Records and Indexes" button for live runtime checks. It then focuses on the more powerful, code-level option: the `VERIFY DATA FILE` and `VERIFY CURRENT DATA FILE` commands, which let a developer target specific tables/fields and supply a callback method invoked on each verification event (message, error, warning, finished, end of execution). A demo component builds three reusable verification methods around this pattern: `_checkTheseTables`, which lets a developer pass a collection of specific tables to check; `_checkAllTablesS2A`, which performs a cheap pre-check across every table by running `ALL RECORDS` + `SELECTION TO ARRAY` inside an `ON ERR CALL` handler and using `GET LAST ERROR STACK` to flag tables that throw runtime errors as candidates for full verification; and `_checkAllTables`, which unconditionally verifies every table. All three funnel into a shared `_verifyTheseTables` method that runs `VERIFY CURRENT DATA FILE` on the target table numbers with a `_callbackVerify` handler collecting only errors and warnings (ignoring informational events) into arrays, then serializes the results via `JSON Stringify` into a timestamped log file under the Logs folder, which is revealed to the user with `SHOW ON DISK`. The note positions this as a way to give administrators and developers fine-grained, scriptable data-integrity checks — for example, running a lightweight sanity sweep before committing to a full verification pass — beyond what the built-in MSC and Admin Window UIs offer out of the box.
