This Tech Note argues that 4D developers should apply the same naming discipline to indexes and table relations that they already apply to tables and fields, rather than leaving 4D to auto-generate opaque UUIDs for these structure objects. It surveys widely-used SQL naming-convention prefixes — such as Pkc (primary key, clustered), Pknc (primary key, non-clustered), Ncu (non-clustered unique), and Nc (non-clustered) — and explains how descriptive names convey index type and purpose at a glance, saving developers from hunting through the Structure Editor to identify a specific index or relation. The note connects this practice to the System Tables introduced in 4D v11 SQL, which let code query index and relation metadata by name, enabling structure auditing (e.g. detecting lost indexes after a recovery, or index types that no longer match field data) and easier programmatic navigation of the schema. Three worked examples illustrate applying a consistent naming scheme across a sample structure. The note does not mandate a specific convention, only that developers pick one and apply it consistently, and is aimed at 4D developers maintaining complex database structures who want faster lookup and better structure documentation.
