This Technical Note (25-09, published September 29, 2025) surveys both traditional and modern approaches to error handling in 4D, motivated by the fact that unhandled errors default to a blocking system dialog that interrupts workflow with no automatic recovery or logging. The traditional mechanism, `ON ERR CALL("MethodName"; ek scope)`, installs a custom handler at one of three scopes — local (`ek local`, highest priority, scoped to a specific code block, must be restored via the saved previous handler afterward), global (`ek global`, typically installed in `On Startup` to catch anything not locally handled), and component (`ek errors from components`, intercepting only errors a component doesn't handle itself) — with a strict execution hierarchy (local, then component, then global, then the default system dialog) and `Method called on error` used to save/restore the active handler around sensitive operations. A worked example (writing to a deliberately read-only file) contrasts the blocking dialog with no handler against a handler that captures `Last errors`, enriches it with method/line/formula/date/version context, and appends it to a persistent `errors.json` log file. The note then covers 4D's modern error primitives: `throw(code; message)` for immediate errors, and the richer `throw(errorObj)` form supporting `componentSignature`, `errCode`, `message` (with XLIFF-based localized lookup by convention `ERR_{componentSignature}_{errCode}`), and a `deferred` flag that postpones error delivery to the end of a method/Try block (useful for components to bundle multiple errors before handing the stack to the host application). Finally, it introduces the `Try(expression)` instruction (4D 20 R4, returns Null on failure and records the error in `Last errors` without halting execution) and the structured `Try...Catch...End try` block (4D 20 R5, including nested Try/Catch), both built around `Last errors` as the canonical error-stack query, illustrated with examples that capture multiple sequential/nested errors into a collection for later analysis or logging — positioning these additions as making 4D error handling more readable, robust, and aligned with modern language conventions.
