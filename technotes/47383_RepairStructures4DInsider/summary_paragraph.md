This Technical Note explains how 4D Insider is used to "repair" a 4D database whose internal data dictionary — the complex arrays/pointers describing which objects exist, how they reference each other, and how they depend on one another — has become corrupted, causing the database to behave strangely or crash. It clarifies up front that 4D Insider does not literally repair the data dictionary; instead, moving all uncorrupted objects from a source database into an empty destination database causes the data dictionary to be completely rebuilt, so the technique only works if the underlying objects themselves are intact. The note lays out five ordered steps that must be followed precisely to preserve internal table/field numbering and object references: (1) empty the Trash in the source database, including moving any leftover tables out of the Trash since tables cannot be truly deleted in 4D; (2) remove all tables from any Explorer groups/folders, since only top-level (ungrouped) tables preserve correct internal references; (3) move all Lists first, so any structure-level choice-list assignments remain intact; (4) move all Tables together in a single move, to preserve their creation-order numbering (important for code relying on table/field numbers); and (5) move everything else, since 4D Insider automatically skips already-copied objects. A dedicated section explains that the password system (Users/Groups) is not carried over automatically — Designer-created users/groups are lost entirely, while Administrator-created ones can be preserved by exporting with USERS TO BLOB in the old structure and reloading with BLOB TO USERS in the new one, with a note that table access-group order (not names) determines reassignment after the move. The note concludes that, despite the number of object types involved, the five-step process is a reliable, well-defined way to rebuild a healthy, working database structure from a damaged one.
