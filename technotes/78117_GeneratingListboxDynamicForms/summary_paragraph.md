Written by Vance Villanueva, this Tech Note contrasts the conventional, form-editor-driven way of building a list box with the newer Dynamic Forms approach (introduced v16R6) of generating the same list box purely through a JSON definition. It first walks through the conventional path for all four list box data-source types: current/named-selection-based (columns bound to field expressions like `[Table_1]ID`, populated via `QUERY`/`ALL RECORDS`), array-based (columns bound to array variable names, populated with `ARRAY TEXT`/`APPEND TO ARRAY`), and collection/entity-selection-based (columns reference a collection or ORDA object variable using the `This` keyword to access object properties, populated via `New collection(New object(...))` for collections or `ds.Table_1.all()` for ORDA entity selections). It notes that once configured, such forms are opened conventionally with `Open form window` or `Open window`. It then pivots to the dynamic approach: instead of placing a list box object in a form editor, a JSON form definition (built either as a literal JSON string or via `New object`/`New collection` calls) is passed to `Open form window`, letting a fully configured, data-bound list box be generated purely from code with no visual form design step. The note details the JSON properties needed for the list box object itself and its columns, across the same four data-source variants (selection, array, collection, entity-selection based), and demonstrates rendering the dynamic form either directly or embedded via a subform. A bundled sample database exercises each of the four calling patterns (selection, array, collection, entity-selection based) and shows the resulting JSON definitions. This positions the note as a practical, side-by-side migration guide for developers wanting to generate list-box-driven UIs dynamically — useful for generic/metadata-driven applications, plugin-generated interfaces, or any scenario where form structure must be determined at runtime rather than fixed at design time.
