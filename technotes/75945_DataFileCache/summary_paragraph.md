This Tech Note explains 4D's data file cache — a chunk of memory managed directly by 4D (not the OS) that holds not just records and indexes but also selections, sets, transactions, sort buffers, and structural definitions — and details how it was dramatically revamped in 4D v11 SQL. It walks through 4D's purge algorithm (removing non-dirty objects first, then flushing and purging again, then spilling other engine objects to a "temporary files" folder) and explains why the "used cache" statistic naturally fluctuates rather than simply climbing to a maximum. It then covers the concrete v11 changes: caches can now grow much larger thanks to improved 64-bit-aware memory management (up to ~4GB versus 2GB in 4D 2004, ideally on a 64-bit OS with at least 8GB RAM), a new 3-way associative addressing scheme replaces sequential search, and BLOBs/Pictures are now stored inside the cache rather than externally. Several "typical" used-cache fluctuation patterns (normal, too-small, and malfunctioning) are illustrated with charts to help developers diagnose cache-sizing problems. Finally it documents new diagnostic tools — `FLUSH BUFFERS(*)`, `GET CACHE STATISTICS`, the "Keep Cache in Physical Memory" option, and the `_USER_IND_COLUMNS` SQL system table for pre-warming indexes into cache. The note is aimed at developers and administrators tuning cache size and troubleshooting performance issues in 4D Server v11 SQL deployments.
