This technical note addresses interprocess variables (prefixed "<>"), a classic 4D language feature now marked deprecated because they are not thread-safe and therefore prevent any method that touches them from running preemptively — a real obstacle as 4D pushes toward multi-threaded, scalable execution via ORDA and object notation. It first reviews 4D's three variable scopes (local "$var", process "var", and interprocess "<>var") with debugger-driven walkthroughs showing how each persists (or doesn't) across method calls and processes, establishing why interprocess variables were historically used for static/dynamic constants and cross-process data sharing. It then presents several thread-safe replacement strategies: 4D Custom Constants, defined via a specially formatted XLIFF XML file placed in the database's resources folder (with `<group>` "theme" elements and `<trans-unit>` entries carrying `d4:value` type-tagged values), which surface in the Explorer window's Constants list just like built-in constants; shared objects and shared collections (`New shared object`/`New shared collection`), which behave like a thread-safe cross between an interprocess variable and a pointer — passed by reference to new processes via `New process` parameters, readable freely, but writable only inside a `Use(...)...End use` block that acts as a mutex, causing other processes' `Use` calls on the same item to block until released, with reference-counted automatic cleanup when no process holds a reference; and the `Storage` object, a special, permanently-alive shared object automatically available to every process, into which arbitrary shared objects/collections can be placed (and later removed via `OB REMOVE` inside `Use...End use`) as a lightweight catalog that avoids having to explicitly pass shared references as parameters. Beyond these, the note discusses simpler alternatives suited to different needs: on-disk files (XML/JSON/text) for deployment- or user-specific settings (mirroring 4D's own use of directory.json and AppData/Application Support folders), dedicated 4D Tables (optionally hidden from REST and, with an underscore-prefixed name, from ORDA auto-completion) for a self-contained single-record settings store, and simple project methods or classes acting as constant-returning accessors or attribute holders. Finally, it lays out a practical three-step migration workflow — identifying all interprocess variables via generated Compiler_Variables_Inter/Compiler_Arrays_Inter methods or a "Find in design" search for the "<>" prefix, determining each variable's actual use (static constant, dynamic constant, or cross-process data share) by inspecting reference lists or exporting method code as text for regular-expression analysis (with example RegEx patterns provided), and finally replacing each occurrence with the appropriate option above — while cautioning that this can be done incrementally, prioritized toward frequently executed methods, and always backed up before automated find/replace operations.
