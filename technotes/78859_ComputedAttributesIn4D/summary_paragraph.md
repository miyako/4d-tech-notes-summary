This foundational Tech Note explains 4D's computed attributes feature (introduced in v19R3), which lets developers define calculated fields — e.g., a full name derived from first/last name — as attributes on ORDA entities without storing redundant data. It first grounds readers in ORDA (Object Relational Data Access, introduced in v17) as an object-notation alternative to 4D's classic current-selection/array-based data access, and in 4D classes (introduced in v18R3, project-mode only) as the mechanism through which computed attributes are defined. To create a computed attribute, developers extend a table's default entity class by creating a {TableName}Entity class (with 'Class extends Entity' auto-inserted) and writing a `Function get {name}() -> $result : Type` that can reference the current entity via This. The note then covers the full interaction surface: a `Function set {name}(...)` to define assignment semantics, a `Function query {name}(...)` receiving an {.operator, .value} input object and returning a {.query, .parameters} object so computed attributes can participate in ORDA .query() calls, and a `Function orderBy {name}(...)` returning a sort string so computed attributes can be used in .orderBy(). It also explains returning related entities/entity selections from a computed attribute (via {Table}Entity / {Table}Selection extended classes) and notes that indexing the underlying real fields improves performance of queries/sorts on computed attributes that reference them. This is essentially the definitive early explainer for how computed attributes fit into 4D's ORDA/classes architecture.
