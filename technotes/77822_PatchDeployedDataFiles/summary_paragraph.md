This third-party Tech Note, contributed by Cam Adams, Justin Carr, and David Adams, addresses a real operational pain point for commercial 4D application vendors: when something goes wrong with a client's deployed data — a bug corrupts records, a user action outpaces 4D Backup's recovery abilities, or diagnostic code is needed to understand a problem occurring only at a customer site — developers need a safe, controlled way to run custom patch code against that data without full access to the customer's environment or an emergency new build. The note surveys the constraints developers commonly face: limited off-site data access due to bandwidth, policy, or legal restrictions; a desire to avoid polluting the main codebase with client-specific hacks; time pressure that rules out waiting for a full release cycle; and reluctance to restart a production server. It proposes building purpose-built 4D components as the delivery mechanism for patches: a component is designed, deployed alongside (or into) the host database, and then triggered to run the patch logic, optionally automated and guarded against being run more than once. The note distinguishes between host data and component data, covering how the patch component interacts with data living in the host database versus data packaged within the component itself, including a tip about using custom constants to simplify this interaction. It also discusses working with external data files and provides guidance on when to lean more or less heavily on embedded SQL for implementing the patch logic, weighing tradeoffs between SQL-heavy and non-SQL approaches. As a field-operations and deployment-support pattern, this note captures durable wisdom about safely patching live customer data, even though its specific tooling (classic components, embedded SQL) reflects the pre-Project-Mode, pre-ORDA 4D v16 era.
