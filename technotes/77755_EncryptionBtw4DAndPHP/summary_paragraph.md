This 2017 tech note by Nicolas Brachfogel of 4D SAS explains how to make 4D's built-in RSA encryption commands interoperate with external PHP code, a common requirement when a 4D backend needs to exchange encrypted data with a web or third-party service. It walks through generating an RSA key pair with GENERATE ENCRYPTION KEYPAIR, encrypting a text string into a BLOB with ENCRYPT BLOB using the private key, and decrypting it again with the public key via DECRYPT BLOB, all persisted to disk as plain documents. It then covers the harder cross-language case: decrypting a 4D-encrypted file from PHP using the phpseclib open-source library, which requires converting 4D's PKCS#1 RSAPublicKey format into the SubjectPublicKeyInfo structure OpenSSL expects, and stripping 4D's proprietary 3-byte (or 4-byte on big-endian) header prepended to every encrypted BLOB. The reverse scenario is also covered: decrypting in 4D a file that was encrypted externally in PHP, which requires manually inserting that same 4D header before calling DECRYPT BLOB. The note is unusually precise about the low-level compatibility gotchas — key format and header bytes — that a developer would otherwise discover only through painful trial and error. Because it focuses on standard RSA cryptography and general interoperability principles rather than any deprecated 4D subsystem, the guidance has aged well: the same commands and caveats still apply to current 4D versions doing classic BLOB-based encryption. It's a good example of a technical note whose narrow technical focus makes it durable across a decade of platform evolution, even though 4D's application development paradigm has otherwise changed considerably since 2017.
