This Tech Note explains 4D's trigger mechanism: a method attached to a table that automatically fires on three database events — On Saving New Record, On Saving an Existing Record, and On Deleting Record — regardless of whether the change originates from a 4D form, a web connection, ODBC, SQL Pass-through, or the IMPORT DATA/RECEIVE RECORD commands. It highlights that 4D v11 introduced parallel execution of triggers across tables (previously triggers executed serially and could block each other), and explains where triggers physically run (always on the machine hosting the database engine — the single-user machine or the 4D Server in client/server mode), which affects how alerts, process variables, and the current selection/record behave. A sample database demonstrates four patterns: stamping records with save timestamps, encrypting sensitive data server-side using variables passed via "Execute on server" and VARIABLE TO VARIABLE, validating input and returning custom error codes to the client through an ON ERR CALL handler, and maintaining relational integrity via cascading triggers (tracked with the TRIGGER LEVEL and TRIGGER PROPERTIES commands to avoid infinite trigger loops). The note closes by cautioning that although v11's concurrent trigger execution improves performance, triggers should still be kept short and fast.
