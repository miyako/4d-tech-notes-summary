This Tech Note addresses a limitation of built (merged) 4D Client-Server deployments: a built 4D Remote Client cannot execute any developer-written code until it successfully connects to a 4D Server, which prevents scenarios like custom connection portals, pre-flight system checks, or automatic failover logic. The solution is 4D's embedded database feature, which lets a compiled standalone structure (.4DC/.4DZ) be merged directly into the built Remote Client via manually added Build XML keys (DatabaseToEmbedInClientMacFolder / DatabaseToEmbedInClientWinFolder under Preferences4D/BuildApp/SourcesFiles/CS), so the client opens and runs this embedded standalone database first — with no data file needed — before transitioning to the server with a call to OPEN DATABASE against a .4dlink file. The note provides a complete worked example implementing automatic server failover: an embedded "Demo_EmbeddedDB" standalone database scans a Resources/Servers directory of numbered .4dlink files in priority order, uses the 4D Internet Commands plugin to UDP-ping each candidate server, connects to the first one found available via OPEN DATABASE, and falls back to a default port 19813 attempt if none respond. Key operational details covered include the requirement that the compiled standalone structure reside alongside the client-server structure at build time, that the 4D Internet Commands plugin must be present in both the embedded database (to compile) and the built client (to run, since plugins normally load from a server cache), and that using a single structure for both standalone and client-server duty is discouraged due to bloated footprint. The note frames this as a general-purpose technique — useful for failover, custom login portals, or diagnostic checks — that gives built 4D Remote Clients much greater flexibility and resilience in production client-server deployments.
