This Tech Note introduces database mirroring as a way to increase 4D Server availability by continuously transferring log files from a principal server to a separate mirror server, so that in case of failure a client application can quickly reconnect to the mirror with no loss of committed data — all without proprietary hardware. It explains the mirroring model: the principal server segments its log file at regular intervals and never runs a backup itself (staying read-write at all times), while each log segment is transmitted to and integrated into the mirror database; backups can instead be run safely on the mirror, since 4D automatically locks the mirror during log integration or its own backup to prevent desynchronization. The note is explicit that mirroring only replicates data changes, not structural changes, making it unsuitable for databases still under active structural development. Because the mirroring component is implemented as a 4D component exposing SOAP-based entry points, the note reviews 4D's web services model (the "Offered as a web service" and "Published in WSDL" method properties, RPC/DOC publication modes, and the required 4D Web Services Server Expansion License) and explains component installation and shared methods in 4D v11. It then walks through the full setup: installing the mirroring component and database methods on the host database, configuring preferences across the Mirrors, Scheduling, Error Handling, and Backup tabs, and understanding the end-to-end flow of the mirroring mechanism.
