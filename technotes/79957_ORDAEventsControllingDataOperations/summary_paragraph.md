This Technical Note (26-03, published March 23, 2026, requires 4D 21) introduces ORDA events, a new event-driven mechanism for controlling database operations that replaces classic table-level 4D triggers with entity-level, object-oriented logic defined directly in Entity classes (e.g. `ProductEntity`, `CustomerEntity`). Seven distinct event functions cover the complete entity lifecycle: `touched` (fires on any in-memory attribute modification, client- or server-side depending on the `local` keyword, cannot stop the action), `validateSave` and `saving` (both run server-side around the save operation and can abort it by returning an error object), `afterSave` (post-save, cannot stop or re-save), and their delete-side counterparts `validateDrop`, `dropping`, and `afterDrop`. Events can be scoped at the entity level (all attributes) or the attribute level (a specific, possibly computed, attribute), with attribute-level events always executing before entity-level ones, and are triggered automatically by ORDA operations (`entity.save()`, `entity.drop()`, `dataClass.fromCollection()`) — never manually — guaranteeing consistent business logic across the UI, REST APIs, and code. Unlike classic triggers, which lock an entire table and process one method with a single `Case of` structure for all operations, ORDA events lock only the affected entity, allowing multiple events to execute concurrently on different records, and return rich error objects (code, message, severity) instead of bare integer codes. The note stresses that classic 4D commands (`SAVE RECORD`, `DELETE RECORD`) only fire classic triggers, never ORDA events, while ORDA methods fire both when classic triggers still exist, and walks through a full worked migration — an order-management system with `Client_Trigger`, `Product_Trigger`, and `Order_Trigger` — converting classic trigger logic into ORDA events including automatic stock management and price calculation, validated by four demonstration test cases.
