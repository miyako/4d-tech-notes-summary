This Tech Note first reviews the fundamentals of 4D's data file (.4DD): it is created alongside a database's structure/project, is the "current data file" that 4D keeps open while the application runs, is recalled across sessions via a `.4Dlink` file stored in the user's platform-specific 4D Favorites preferences folder, and is best placed on fast local storage (SSD) separate from the structure for both performance and security reasons in production deployments. It then demonstrates, with a hex-editor comparison (HxD), that an unencrypted data file stores field values in a human-readable, recoverable form, motivating 4D v18's new datafile-level encryption feature. Encryption is applied per-table via a new "Encryptable" property in the Structure Editor, and the actual encryption/decryption operation is performed either through the Maintenance and Security Center's Encrypt tab (with a passphrase strength meter) or programmatically with the `Encrypt data file` command, which takes the structure path, data file path, and passphrase, and returns the path of a "Replaced Files…" backup folder. The passphrase is SHA-256 hashed into an AES-256 symmetric key, which can optionally be exported to a `.4DKeyChain` JSON file (single or multi-key "Master" keychains) for unlocking via USB drive or code. Unlocking at runtime is handled through a discovery chain — an in-memory keychain, then a `.4DKeyChain` file on a connected drive, then explicit code via `Discover data key`, `ds.provideDataKey()`, or the legacy `Register data key` command. The note also shows how to toggle the "Encryptable" flag programmatically in Project mode by editing the `catalog.4DCatalog` XML with `DOM` commands (not possible in binary mode), and covers re-encryption, passphrase rotation, and full decryption workflows, both via MSC and via the `Encrypt data file` command's parameter variants.
