This tech note contrasts the notarization experience between 4D v18 and v17 as macOS Catalina's mandatory notarization requirement took effect, showing that 4D v18's updated "Sign application" build feature made the process dramatically simpler than v17's. For v18, the workflow is nearly turnkey: check "Sign application" and enter a certificate name during the build, optionally verify the signature with `spctl -av`, zip (or DMG) the app, generate an app-specific Apple ID password, then run `xcrun altool --notarize-app` to upload, poll status with `xcrun altool --notarization-history`/`--notarization-info` (checking for warnings via a returned `LogFileURL`), and finally staple the ticket with `stapler staple` and re-verify with `spctl -av`. By contrast, a v17-built app signed with the same "Sign application" feature would retain outdated inner-binary signatures that trigger notarization errors, so the note details a much more manual workaround for v17: building without automatic signing, understanding and authoring an entitlements property list (explaining sandboxing/hardened-runtime requirements), and then performing "signing inside out" — individually re-signing each nested component from the innermost outward, covering Native Components, Frameworks, SASL Plugins, Resources, and finally the top-level MacOS executable folder, each requiring its own `codesign` invocation with the correct entitlements and options. To make this tedious inside-out process manageable, the note also shows how to wrap all the individual signing commands into a single automation script. The note frames v18 as effectively solving Catalina notarization "for free," while giving v17 users (who couldn't yet upgrade) a concrete, if laborious, path to compliance.
