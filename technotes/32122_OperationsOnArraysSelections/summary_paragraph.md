This Tech Note explores the relationship between two related but distinct 4th Dimension record-subset mechanisms: sets, which have existed since the earliest versions of the product and represent stored query results on one or more tables, and named selections, introduced in version 6, which serve a similar purpose but behave differently in several notable ways. The note highlights why sets are valuable — they let developers store query results and combine them using classic set operations (union, intersection, and difference), enabling complex queries to be broken into simpler sequential steps that are easier to write, read, and maintain. Because named selections don't natively support the same union/intersection/difference operations as sets, the tech note provides custom methods that let developers handle named selections in the same set-like manner, effectively bridging the gap between the two mechanisms. Beyond solving this specific problem, the note is explicitly framed as a demonstration of how easy it is to build custom commands in 4D that extend the language to match a developer's specific needs, making it as much a lesson in extensible method design as it is a solution to the selections/sets gap. The featured technology is 4D's core data-selection model — sets, named selections, and their combination operators — reflecting foundational, everyday concerns for 4D developers writing anything beyond simple single-query record retrieval in the pre-SQL-engine era of the product.
