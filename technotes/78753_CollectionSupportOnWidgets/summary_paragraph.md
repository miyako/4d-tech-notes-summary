This tech note introduces a new v19 feature letting three form objects — pop-up/drop-down lists, combo boxes, and tab controls — define their programmatic values via an object containing a collection instead of the classic array-based data source. The new pattern sets the object's Expression Type to Object and points it at a form variable (e.g. Form.continents_o) that carries three key properties: values (a Collection holding the option list), index (the 0-based position of the current selection, used by drop-downs and tab controls but not combo boxes), and currentValue (the currently selected/displayed value, also usable as a placeholder). The note contrasts this with the older approach, which required declaring a typed array with one of eleven ARRAY-family commands, manually managing indices, and relying on process variables that make cross-process/cross-form data sharing awkward. Collections, by contrast, are declared generically (C_COLLECTION or the var keyword), can hold mixed types, expose roughly twice as many manipulation methods as arrays (e.g. collection.push(), .sort(), .map(), .join()), and — critically for forms — can be bound to Form variables and passed cleanly between processes via the DIALOG command's parameter, avoiding process/interprocess variable plumbing altogether. A bundled sample database demonstrates each of the three widget types being initialized this way, including generating a large date range dynamically with a For loop and collection.push(), and using collection.sort() to alphabetize combo box entries with automatic-insertion enabled.
