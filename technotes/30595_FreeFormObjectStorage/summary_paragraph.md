Written by Dave Dell'Aquila (Senior 4D Evangelist) as Technical Note 03-51, this note tackles a recurring database-design problem: needing to store miscellaneous, loosely structured application data — window coordinates, default field values, custom field names, user-adjusted column widths, number formats — without creating a dedicated table or field for every "trivial" setting. The proposed solution is a single generic project method called `cObject`, dispatched via a `Case of` statement on its first parameter ("get", "set", "save", plus internal helpers like "$load", "$loadPref", "loadForUpdate", "$new", "rename", "delete", and "init"/"startup"), backed by one `Objects` table containing an indexed `CollectionName` field and a `Members` subtable holding `Members'Name` (a subfield) and `Members'Data` (a BLOB). Any named "collection" of settings (for example, keyed by `Current user` or `Current machine owner`) is created automatically the first time it's used, and individual named "member" values within it are stored using `VARIABLE TO BLOB`/read back using `BLOB TO VARIABLE`, letting the mechanism transparently handle any 4D data type — Boolean, date, number, text, even pictures — as long as the caller loads/reads into a variable of the correct type. A `loadForUpdate` operation implements simple multi-user safety, polling `Locked()` against a `Tickcount` timeout before acquiring the record for writing. The note demonstrates usage with a per-user preferences dialog (loading four values on `On Load`, saving them on `On Clicked` via a Save button) and a second dialog that lets users switch between multiple named collections on the fly, and includes the complete `cObject` source listing (revision 9, dated 5/10/98) at the end.
