This Tech Note by Walt Nelson is Part 2 of a three-part series on developing with 4D Server (Part 1 covered the advantages of 4D Server multi-user development; Part 3 would cover naming conventions), focusing specifically on setting up a multi-developer password system. It opens by explaining the concept of dividing a large project into functional Modules — illustrated using the standard Invoices example database split into five modules (Main/Customers, Invoices, Products, Payments, Mail) — and outlines the factors that should guide module boundaries: Universality (shared functions belong in the top-level Main module), Interdependence (tightly coupled functions may be grouped), Timing/delivery schedule, Availability of resources, and Degree of difficulty/complexity. It then walks through setting up Users and Groups in an example "Multi-Developer" database, explaining 4D's ownership model: objects (Files, Forms, Procedures) are owned by Groups, not individuals; the top-level Designer belongs to every group by default and thus can view/modify anything in Design mode, with the sole exception that the Designer cannot modify passwords or group memberships created by the Administrator; the Administrator can Export/Import Users and Groups records (a privilege no one else has) but otherwise has no default design privileges beyond compiling; and because only the Designer has ownership across all groups, only the Designer and Administrator can Compile the structure, and only the Designer can open it with 4D Insider (a limitation the note says can be worked around, discussed later). Using the Payments module as a running example, the note demonstrates step-by-step how to assign Group ownership to a specific File (via the File attributes dialog's Owner pop-up), verifying via Runtime mode that a non-member user (Mary from the Mail module) is denied access to the [Payments] file definition; the same ownership-assignment principle is then repeated for Forms/Layouts (via the Layout dialog's Owner pop-up, explicitly distinguishing "Owner" — who can modify in Design mode — from "Access" — who can use it at Runtime, which the note deliberately leaves open to All Groups) and for Global Procedures (via the Procedure dialog's Owner pop-up, with the same Owner/Access distinction). It closes with a discussion of the practical downside of this multi-tiered password approach — restricted Compile and 4D Insider access limited to the Designer/Administrator — offering a workaround of periodically distributing "Single-User Copies" of the structure with a special, less-restrictive Designer password so other developers can inspect (but not modify, since it's not the Master Structure) objects outside their module. As a foundational guide to 4D's classic binary-structure, Design Mode-based password and ownership system for coordinating multiple developers on one shared 4D Server database, its underlying goal — module-scoped ownership to prevent developers from stepping on each other's code — remains a sound engineering principle, but its specific mechanics (binary structure file ownership locks, single-Designer 4D Insider access, and "Global Procedures" terminology) are dated relative to modern 4D's Project Mode and Git-based collaborative workflows introduced decades later.
