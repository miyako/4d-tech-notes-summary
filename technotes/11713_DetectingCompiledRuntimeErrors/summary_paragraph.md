This Tech Note addresses a frustrating class of bug for 4D developers in the mid-1990s: code that runs correctly in interpreted mode but produces a runtime error only after being compiled. It explains that the 4D interpreter is more permissive about data types than compiled code, so certain type mismatches simply pass silently while interpreted but trigger a hard runtime error once compiled — the note enumerates roughly a dozen categories of such compiled-only runtime errors, with particular focus on the EXECUTE command, which dynamically executes a string of 4D code and can receive parameters whose types don't match what the executed code expects. Since these errors only appear post-compilation, and compiling+testing an entire application is time-consuming, the note presents a practical workaround: developers can declare process variables with explicit, strict types (matching the types expected by parameters going into things like EXECUTE) and use them in interpreted mode in place of the untyped/generic values that would otherwise mask the mismatch, so 4D's interpreter throws an error the developer can catch and fix before ever compiling. The note walks through a concrete before/after example demonstrating a parameter type mismatch that passes silently by default in interpreted mode but is caught immediately once the variable is declared with the correct explicit type, letting developers iteratively harden their code against compiled-mode failures without needing to run a full compile cycle after every change. Featured technology centers on the 4D Compiler's stricter type-checking behavior relative to the interpreter, the EXECUTE command as the primary example of an error-prone dynamic construct, and the use of explicitly typed process variables as a debugging technique.
