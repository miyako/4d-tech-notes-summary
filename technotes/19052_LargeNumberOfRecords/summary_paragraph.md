This 2001 Tech Note by Thomas Maul of 4D Germany tackles the practical problems of very large 4D tables, noting that 4D's 16-million-record-per-table limit is rarely hit but that speed problems from multi-field queries against big selections show up long before that limit is reached. Using a factory sensor-logging example (two halls x five assembly lines x ten sensors x one reading per second = 8.6 million records/day), it shows that a naive schema with five separately indexed fields forces 4D to run several sequential QUERY commands, each returning huge intermediate selections that must be intersected. The proposed fix is a "combined key" or "combined index": a Trigger (firing on On Saving New/Existing Record Event) computes a single string key from Sensor ID, Assembly Line, and Production Hall (e.g. "003-02-01") and a separate Longint TimeStamp from Date and Time (days since !01.01.80! times 86400, plus seconds), both saved to indexed fields; this lets a six-line multi-field query collapse into two or three single-field queries against the combined key/timestamp, dramatically cutting response time and server load, and even supports wildcard queries like "001@" for partial matches. A second section addresses reducing the record count itself: aggregating raw per-second readings into per-minute (or longer) summary blobs/arrays with precomputed min/max/average, archiving older detailed data out of the live database via Blob to Document, and reloading it on demand. Finally, a "clustered index" / query-cache technique is shown for a mail-archive-style full-text search scenario, using per-word Boolean sets (BOOLEAN ARRAY FROM SET, COMPRESS BLOB, CREATE SET FROM ARRAY) to make repeated word searches near-instant, illustrated with real numbers from a German NUG-style archive (21,000 messages, 69,500 unique words, ~70,000 sets).
