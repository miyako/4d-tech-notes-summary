This second half of a two-part series by Tai Bui goes deep into 4D's database mirroring feature as a high-availability/disaster-recovery mechanism, following Part I's overview of backups and general mirror setup. It explains that a mirror is typically two full 4D Server copies running on separate physical machines, one acting as the principal (actively used) database and the other as a standby mirror, distinguished at startup by application-level logic (e.g., checking for a marker file). It contrasts hot standby (fully synchronized, every operation immediately reproduced) with warm standby (periodically synchronized) and notes that 4D mirrors are typically configured as warm standby, which 4D's architecture makes low-risk. The mechanics are laid out step by step: operations on the principal database are continuously written to a current log file; on a regular interval (often via a stored procedure) the `New log file` command closes that log and starts a fresh one, after which the closed log is transferred to the mirror machine; the mirror server then periodically applies pending logs to its own datafile using the `Integrate Mirror Log File` command, keeping it a near-real-time replica. The recovery section then addresses the actual disaster scenario — e.g., an ungraceful shutdown corrupting the principal datafile — and prescribes using the mirror's datafile (trusted over the damaged principal's) combined with the principal's still-intact current log file to reconstruct a fully up-to-date datafile, since the warm-standby mirror may be missing only the most recent, still-unshipped operations. Two integration paths are covered: manually running `Integrate Mirror Log File` on the mirror itself while it is still running (efficient since it's local), which requires carefully pairing the resulting updated datafile with its correctly-renamed log file (`{databaseName}.journal`) before relocating them back to the principal machine; and an alternative in which 4D automatically integrates the log. The note closes with the final step of restarting both production and mirror servers once the datafile/log pair is correctly restored. This positions the note as essential, hands-on operational guidance for any 4D deployment with business-critical uptime requirements, translating 4D's mirroring feature from a conceptual safety net into a concrete, executable recovery runbook.
