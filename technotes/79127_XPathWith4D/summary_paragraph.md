This Tech Note walks through XPath, a W3C query language for navigating XML document trees, and its now-stabilized support in 4D through the DOM (Document Object Model) command set. It highlights a critical compatibility distinction between two internal XPath implementations: the original "XPath 4D" (available since v11, which lets a path expression like `"root/test2"` implicitly resolve relative to any node) versus the standard XPath introduced in v18R3, which requires the root to be specified explicitly (`"/root/test2"`) — code written against one implementation silently returns nothing under the other, making this the single most important gotcha the note calls out. It then builds up XML/XPath fundamentals — the seven node types, the root element, atomic values (returned by `DOM READ XML ELEMENT VALUE`/`DOM READ XML ATTRIBUTE BY NAME`), and node relationships (children via `DOM Read first child XML element`, siblings via `DOM Read previous/next sibling XML element`, ancestors via `DOM Read parent XML element`, and descendants, which without XPath require nested manual traversal loops) — before showing how a single `DOM Find XML element` call with an XPath expression like `"/bookstore//book"` collapses that manual traversal into one line. It surveys XPath syntax essentials (node selection, `[...]` predicates, wildcard "unknown node" selection, axes, and operators returning node-sets/strings/booleans/numbers, noting 4D always returns a node-set on match) before applying the concepts to two practical 4D "user stories": reading the database's publication name from a parsed `settings.4DSettings` XML file via an attribute XPath expression, and extracting the id/uuid/name of every table by exporting the live structure with `EXPORT STRUCTURE` and iterating matched `/base/table` nodes with `DOM Get next sibling XML element`. The note positions XPath as a powerful but historically underused 4D tool that meaningfully shortens code for structure/settings introspection and other XML-processing tasks once developers are aware of the classic-vs-standard implementation split.
