This Tech Note addresses the challenges of managing 4D component dependencies — reusable code packages that extend 4D projects with built-in features (4D SVG, 4D NetKit, 4D View Pro, 4D Write Pro Interface) or community/GitHub-shared functionality — where version drift, update inconsistency, and interpreted/compiled mode mismatches commonly cause integration problems. The core technical approach centers on two JSON configuration files placed in a 4D project: dependencies.json, which declares required components (local or GitHub-based, e.g. "github": "JohnSmith/theComponent"), and the optional environment4d.json, which overrides component search paths for local or multi-project development setups without polluting version control. 4D resolves components in priority order — the project's Components folder first, then environment4d.json paths, then dependencies.json paths, falling back to built-in components. Beyond the JSON files, the note covers the graphical Project Dependencies panel (Design → Project Dependencies) for adding, updating, and monitoring dependencies with origin tags (4D Component, dependencies.json, Environment, Project Component), and dependency rules for GitHub components (Latest, Up to Next Major/Minor Version, Exact Version, Follow 4D Version) tied to semantic versioning and LTS/R-release tag naming conventions. It explains the structural difference between interpreted components (.4dbase folders, usable only in interpreted host projects) and compiled components (.4DZ files, usable in both modes and required for macOS notarization-friendly deployment). A worked demo publishes a private "jauge" (gauge) component on GitHub, tags a release following 4D's version-naming convention, adds a GitHub personal access token, and consumes the dependency in a host project. The note closes with troubleshooting guidance for common failures: undetected/unapplied updates, malformed GitHub release archives, access-token issues, and unexpected automatic version changes from 4D's background update-check script.
