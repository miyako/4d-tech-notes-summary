This Tech Note explains the "sleeper process" technique for improving 4D application performance and interface modelessness by recycling a single paused process to perform routine tasks rather than repeatedly launching and discarding new processes. It opens by discussing modelessness as a design goal — letting users interact with multiple tasks simultaneously — and explains that 4D's process model, while excellent for enabling this, carries real overhead: every new process must allocate memory for variables and build a current selection for every file, and this cost is magnified over a network with 4D Server. The core technique is three procedures: LaunchSleeper starts a process and immediately pauses it (via PAUSE PROCESS, not CALL PROCESS, to avoid needing a layout and to save processor cycles); the Sleeper procedure loops forever, executing whatever action string is stored in an interprocess variable each time it's resumed, then pausing itself again; and WakeUpSleeper sets the action string and resumes the sleeper process to invoke it. The note demonstrates calling WakeUpSleeper("AddNewRecord") as a simple example and stresses that the sleeper must be a global (not local) process since it typically needs to access record data. It then sketches extensions: queuing multiple actions in an interprocess array for batch processing, adding task priority handling, dynamically spinning up additional processes if the sleeper is busy, and logging usage to tune the number of paused processes for optimal performance. The featured technology is squarely 4D's classic process management commands (New process, PAUSE PROCESS, RESUME PROCESS, EXECUTE), targeted at both single-user 4th Dimension and multi-user 4D Server deployments. The summary closes by framing this as one tool among several for balancing modelessness against memory/performance constraints in both single-user and server-based 4D applications.
