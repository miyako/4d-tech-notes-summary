This Tech Note provides a practical, step-by-step guide for digitally signing a 4D Windows application package (the .exe produced by merging a 4D Volume Desktop with a compiled structure) using Microsoft's SignTool utility. It opens by explaining the security rationale for code signing: it proves the application hasn't been tampered with since the developer's original build and confirms the signatory's identity, whereas an unsigned executable can trigger antivirus warnings and lacks any tamper-evidence guarantee. The walkthrough covers three phases: Generation, where a self-signed certificate is created via PowerShell's New-SelfSignedCertificate cmdlet (specifying subject, DigitalSignature key usage, and a friendly name), stored in the local certificate store; Export, where the Microsoft Management Console (MMC) is used to locate the certificate under Certificates > Personal > Certificates and export it as a password-protected PFX file, choosing either TripleDES-SHA1 or AES256-SHA256 encryption; and Signatures, where the actual signtool.exe sign command is run from a terminal, with distinct syntax shown for SHA1 (referencing a legacy VeriSign timestamp server) versus SHA256 (referencing a Symantec SHA256 timestamp server), plus a signtool.exe verify command to confirm the resulting signature. The note also points out that 4D's own executables ship self-signed in both SHA1 and SHA256 by default. Overall it's a focused, task-oriented reference aimed at developers who need to sign their compiled Windows builds before distribution, referencing Microsoft's own SignTool documentation and the Windows SDK as prerequisites.
