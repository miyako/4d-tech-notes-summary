Jean-Yves Fock-Hoon, QA Manager at 4D, explains one of 4D's distinctive strengths — the ability to add fields or change a field's type on the fly without exporting and re-importing all data — and the subtlety behind how it actually works internally. Using a concrete demonstration (retyping an Alpha field to Real and back), he shows that 4D does not rewrite a record's on-disk format unless that specific field is modified and the record is explicitly resaved; until then, 4D simply reinterprets/converts the stored value for display purposes only, which means a value can be recovered by reverting the field's type even after such a 'conversion' appears to have happened. This lazy-reformatting behavior is both a safeguard against accidental data loss and a performance optimization (avoiding needless resaves of large records), but it has a hidden cost: when a table contains records saved under different historical formats, SELECTION TO ARRAY and similar operations fall back from an optimized internal path to a slower, format-checking traditional path, measurably increasing execution time in Fock-Hoon's benchmark. He provides a full resave routine (M_ResaveAll-style) that loops over every table and field using Table, Table name, Count tables, and Count fields, forcing a computed change on each field type (adding an empty string to Alpha/Text, adding 0 to numeric/Date/Time fields, reassigning BLOBs and pictures, an OR FALSE for Booleans) so every record gets rewritten in the current, consistent format — including an undocumented technique using GET FIELD TITLES and the Field function to enumerate and resave subtable subfields, which the note explicitly flags as unsupported and subject to discontinuation. The technical note closes by warning that legacy databases carried forward across many 4D versions are especially prone to this format drift and recommends periodically resaving all records as routine maintenance, alongside 4D Tools' data-recovery capabilities, to avoid both performance degradation and corruption risk.
