This third-party Tech Note by David Adams addresses a practical annoyance with 4D's native SQL support: quick SELECT-based lookups (e.g. fetching a related field's value without disturbing the current record/selection) are convenient, but hardcoded SQL text referencing table/field names breaks silently — without compile-time warnings — if those structure elements are later renamed, retyped, or deleted. The note walks through the common problems (references versus literals, renaming tables/fields, a "safe but inefficient" dynamic-lookup fallback, and the risk of field retyping) before introducing its proposed solution: a "Named SQL Lookup" system where each lookup is declared once by name with its lookup field, result field, and a "magic string" describing the expected field-pair types (e.g. LongFromText, BoolFromLong), then invoked safely elsewhere by that name. The system includes a review/validation/sample-code screen listing all declared lookups with their tables, fields, and any validation errors (such as unsupported result types or fields that have since been retyped) so problems surface during development rather than after deployment, plus a visual "Named Lookup Builder" dialog to construct declarations without hand-writing them. The note recommends using custom constants (via the free 4D Pop tool) instead of raw magic strings for readability, while acknowledging constants are less portable between systems, which is why the sample doesn't use them directly. A pros/cons section weighs the benefits (safety, validation, discoverability) against limits of the named-lookup approach, and a design-choices section explains stylistic decisions such as storing lookup definitions in arrays and why the code is split into so many small routines. The conclusion frames this pattern as a reusable utility worth adapting into any 4D codebase that leans on SQL lookups, and the sample database later serves as the base for the related error-logging Tech Note 15-19.
