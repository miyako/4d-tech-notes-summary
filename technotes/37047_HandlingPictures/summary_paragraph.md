Gerard Czwiklinski of 4D S.A. shows how to manipulate a picture's raw pixel bytes directly by converting it to an uncompressed 24-bit BMP inside a BLOB with PICTURE TO BLOB(picture;blob;"BMPf") — relying on QuickTime for the format conversion — and then reading it back with BLOB TO PICTURE once the bytes are modified. After explaining the 24-bit BMP layout (a 54-byte header, 3 bytes of RGB per pixel, rows padded to a multiple of 4 bytes, and rows stored bottom-to-top), the note walks through implementing several pixel-level filters as GCZ_-prefixed methods bundled in the demo database: vertical and horizontal mirror flips (simple row/pixel swaps that reuse the original BLOB), 90-degree left/right rotations and cropping (which require a freshly sized BLOB, since width and height swap for non-square images, plus a copied and patched header), grayscale conversion (first a naive average of R/G/B, then a perceptually corrected weighted formula: 0.3×Red + 0.6×Green + 0.1×Blue), color negation (255 minus each channel), and brightness adjustment (adding a value between -255 and 255 to each channel). A dedicated section on data typing shows that typing the BLOB offset variable as a longint rather than letting 4D default to real numbers took a negation filter from 2340 ms down to 307 ms, and keeping arithmetic operands the same type saved a further 36 ms. A companion section on memory usage walks through how converting a 44 KB compressed JPEG to an uncompressed BMP can balloon to 2.25 MB — 50 times larger — and, with a second working BLOB during rotation, can peak at 5.5–6.75 MB, suggesting pre-computing exact BLOB sizes, avoiding unnecessary memory bumps (unneeded on the new 4D 2004 memory scheme), handling large pictures on disk, or reconverting the result back to a compact format like JPEG afterward.
