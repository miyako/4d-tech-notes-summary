This Technical Note details a major upgrade to Hierarchical Lists in 4D v11 SQL, centered on the ability to display a single Hierarchical List language object (list reference ID) simultaneously through multiple independent form objects — whether on the same form or different forms — without having to rebuild the list separately for each display, a limitation that existed in all prior 4D versions. It explains that while most list characteristics remain shared across all form representations of a list, a few properties are now unique per form object: the currently selected items, the expanded/collapsed state of items, and the scroll cursor position. To support this, many existing list-manipulation commands (SET LIST ITEM, GET LIST ITEM, SELECT LIST ITEMS BY POSITION, Count list items, Selected list items, List item parent, List item position, SET/GET LIST ITEM PROPERTIES, and the renamed DELETE FROM LIST / INSERT IN LIST, formerly DELETE LIST ITEM / INSERT LIST ITEM) gained a new optional leading parameter syntax — COMMAND(*;"objectname";...) — that lets code target a specific form object rather than all form representations of the list, while the older list-reference-ID-only syntax remains valid for general, non-form-object-specific operations. The note documents several entirely new commands introduced alongside this change: SET LIST ITEM FONT, Get list item font, Find in list, SET LIST ITEM ICON, GET LIST ITEM ICON, SET LIST ITEM PARAMETER, and GET LIST ITEM PARAMETER, and clarifies that object-name references also support a wildcard character (e.g. "HL@") to affect or query all form objects whose names share a prefix. It further explains a precedence rule: once a Hierarchical List command (e.g. SET LIST ITEM FONT) is used to set a display property on a form object, it overrides and locks out any conflicting setting made via the Property List in Design mode or the general Object Properties theme commands (FONT, FONT STYLE, FONT SIZE), which likewise now also work with Hierarchical List objects and can be applied per-form-object using the same optional-object-name syntax. Accompanied by a sample database demonstrating two form objects tied to the same underlying list with independently different selections and expand/collapse states, this note documents a substantive, developer-facing UI/UX enhancement delivered as part of the broader 4D v11 SQL release.
