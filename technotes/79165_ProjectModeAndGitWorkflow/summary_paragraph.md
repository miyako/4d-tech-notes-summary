This Tech Note explains why 4D's project mode (introduced in v18, exporting a binary .4DB structure into discrete text files via File > Export > Structure to Project) is the ideal pairing for Git version control, and walks through the practical mechanics of using Git with a 4D project database. Because project mode stores each method as a `.4dm` text file and each form as a JSON-formatted `.4DForm` file inside a `Project/Sources` directory (alongside the XML `catalog.4DCatalog` schema file), all of it is naturally diffable and trackable the way binary structures never were, and project files stay synced bidirectionally with the 4D IDE. The note covers local repo setup (`git init`), the recommended `.gitignore` (autogenerated since v19R2's "Create a .gitignore file" preference) to exclude large/sensitive files like the data file, and remote repo setup on GitHub via `git clone` or `git remote add origin`. It then walks through core Git CLI commands with a running example — modifying a project method, then using `git status`, `git add`, `git commit -m`, `git log`, and `git reset --hard <hash>` to inspect, stage, snapshot, review history, and roll back changes — plus `git push --set-upstream origin main` to sync with GitHub, with a callout that `git revert` is preferred over `git reset` for undoing already-shared/public commits. Finally, it contrasts two team collaboration models: a Centralized Workflow, where each developer clones the shared remote, commits locally, and uses `git pull --rebase` before pushing (simple but merge-conflict-prone for larger teams), versus a Feature Branch Workflow, where developers create per-feature branches (`git checkout -b`), push them for review as GitHub pull requests, and merge into main once approved — which scales better with team size. Overall the note positions Git plus project mode as the modern standard 4D development practice for both solo developers (history/rollback) and teams (collaboration, code review via pull requests).
