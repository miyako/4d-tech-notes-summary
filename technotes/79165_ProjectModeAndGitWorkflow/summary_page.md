# Tech Note 23-07: Project Mode and Git Workflow

**Author:** Nhat Do, Technical Services Engineer, 4D Inc.
**Published:** April 18, 2023 | **Product/Version:** 4D v19 | **Platform:** Mac & Win
**Page:** https://kb.4d.com/assetid=79165
**Download:** https://kb.4d.com/DLTN/TN/2023/23-07_ProjectModeAndGitWorkflow.pdf

## Proposition
Binary 4D databases store all code and forms inside a single opaque structure file, making meaningful version control impossible. 4D's project mode disperses that code into individual text files, making it a natural fit for Git — this note explains how to set up and use Git (locally and via GitHub) with a 4D project application, both solo and in teams.

## Key Points
- **Project mode basics:** generated by exporting a binary structure (File > Export > Structure to Project) or creating a new project directly; recognizable by the "Classes" category in the Methods explorer and a `.4DProject` anchor file.
- **Text-based storage:** methods are stored as `.4dm` files and forms as JSON `.4DForm` files inside `Project/Sources/Methods` and `Project/Sources/Forms`, kept in sync with the 4D IDE automatically.
- **Local Git setup:** `git init` inside the project's root directory creates the `.git` tracking folder; a `.gitignore` (auto-generatable since v19R2) excludes files like the data file that shouldn't be tracked.
- **GitHub remote setup:** either `git clone <url>` to start a new local project from an existing remote, or `git remote add origin <url>` to link an already-initialized local project.
- **Core CLI workflow:** `git status` (see changes), `git add` (stage), `git commit -m` (snapshot), `git log` (history), `git reset --hard <hash>` (roll back local changes), `git push` (sync to remote).
- **Undo guidance:** use `git reset` for private/local undo, but `git revert` for undoing changes already shared/pushed publicly.
- **Centralized workflow:** all developers clone one remote repo, commit locally, and `git pull --rebase` before pushing — simple, good for small teams.
- **Feature branch workflow:** developers branch per feature (`git checkout -b`), push the branch, open a GitHub pull request for review, then merge to main — scales better with team size.

## Featured Technology
- **4D project mode (.4DProject / .4dm / .4DForm)** — text-file-based structure that makes 4D code diffable and Git-trackable.
- **Git CLI** — command-line version control tool used for local and remote change tracking.
- **GitHub** — cloud hosting service for remote repositories, pull requests, and team collaboration.
- **.gitignore** — configuration file (with a 4D-generated default) that excludes non-trackable files like the data file.

## Best Practices Highlighted
1. Use at least 4D v18 (ideally v19R2+ for auto-generated `.gitignore`) when adopting project mode with Git.
2. Exclude large/sensitive files (e.g., the data file) from tracking via `.gitignore`.
3. Prefer `git revert` over `git reset` once changes have been pushed to a shared/public remote.
4. Choose a feature-branch workflow with pull-request review over a centralized workflow as team size grows.

## Context / Positioning
Published as project mode adoption was becoming the majority practice among 4D developers (per the note's anecdotal usage data), this Tech Note reflects 4D's broader modernization push — pairing project mode, classes/ORDA, and now standard software-engineering practices like Git-based version control and GitHub collaboration — to bring 4D development in line with mainstream software engineering workflows.
