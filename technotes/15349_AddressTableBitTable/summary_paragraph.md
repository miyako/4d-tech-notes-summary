This Tech Note by Olivier Deschanels (4D, S.A.) continues directly from TN 01-29 ("The 128th Byte") to explain how 4D's classic engine locates individual records inside its single, 128-byte-block-organized data file. Each record begins with a 4-byte "tag" that encodes the 4D version and the platform (Mac or Windows) it was saved on, because Mac and Windows order integer/longint bytes differently; 4D uses this tag to decide whether byte swapping is needed when reading a record, and Deschanels explains why the engine's designers chose to store the origin platform rather than picking one fixed byte order (to avoid perpetually penalizing Mac users with swap overhead). Because scanning the raw file for tag markers is unreliable — text data can coincidentally match a tag's hex pattern — 4D instead maintains per-table Address Tables: a two-level structure with a 4096-row Primary Address Table (PAT) pointing to Secondary Address Tables (SATs), each holding up to 4096 record addresses and sizes, letting the engine locate any of up to 16,777,216 records with a simple formula (`(n/4096)+1`) rather than a linear scan. The note also covers the parallel bit-table mechanism — one bit per 128-byte block, tracking free vs. occupied space, addressed via a Bit-table-address-table (BTAT) — and the tradeoffs of the "Completely Deleted" table option, which controls whether deleted records are actively zero-tagged (safer, slower) or left recoverable in place (faster, riskier for data that must not resurface). It closes with practical advice: use `SELECT ALL`/`APPLY TO SELECTION` to force records to be re-saved in the deployment platform's native byte order for optimal read performance after moving a data file between Mac and Windows.
