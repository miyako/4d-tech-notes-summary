With 4D v18 R3's class-based object-oriented programming (Class Constructor, Class extends, class functions) maturing, this Tech Note tackles a common community request: how to implement a singleton — a class instantiated once and shared across all of a database's processes. It first dismisses two conventional approaches as inadequate: interprocess variables can't be used in preemptive process contexts, and shared objects/collections accessed via `Storage` still leave developers manually managing locks across every process and component that touches them. The proposed alternative builds "static" class properties by defining them as shared objects/collections stored on a per-class basis and exposed through helper functions `has_static`, `get_static`, and `remove_static` on a base `Object` class, so any subclass can lazily create and retrieve a shared property that behaves like a true static member. A `File` class then extends `Object`, uses `get_static` to obtain its static property, and layers in `_path`, `_owner`, `_retain`, and `_reference` sub-properties, implementing `retain`/`release`/`owner`/`in_use`/`open` methods that together form a reference-counting scheme: a process must successfully "retain" the file object before opening it, and any other process attempting to open the same path while it is in use will fail the `.open()` call, deliberately avoiding a semaphore-based lock in favor of counting active users. All shared-object access is wrapped in `Use...End use` blocks for proper concurrency safety. The attached sample project demonstrates that two processes trying to open the same file concurrently correctly result in only one succeeding, validating the singleton/concurrency-guard behavior. The note situates this technique squarely within 4D's push toward OOP best practices as ORDA, classes, and preemptive processes become central to modern 4D development.
