Written by Gary Brocks, a 4D Evangelist at 4D, Inc., this Tech Note lays out a menu system design that is easy to implement and maintain over a database's lifetime, grounded in Apple's Human Interface Guidelines principle that menus and menu items should remain consistently present and simply be grayed out when unavailable, rather than appearing and disappearing. It identifies three basic "areas" of a typical 4D application -- a splash screen, a list of records, and a detail view of a single record -- and observes that naively enabling/disabling individual menu items by hand as users move between these areas scales poorly (e.g., 36 items across 6 menus means 108 enable/disable operations across three areas). The proposed "4D RAD" system instead creates four menu bars: one each for the splash screen, list view, and detail view (each carrying the same menus/items but with different ones enabled or disabled), plus a fourth, deliberately empty menu bar. It relies on the distinction between the "current" menu bar (set via the MENU BAR command) and menu bar "activation" (controlled by a form's Active Menu Bar checkbox and its Associated Menu Bar property, whose menus get appended to the current bar) -- documented through seven concrete test scenarios of how MENU BAR, Associated Menu Bar, and Active Menu Bar interact. By assigning the shared empty menu bar as every form's Associated Menu Bar and turning on Active Menu Bar everywhere, any current menu bar switched in via a single MENU BAR(n) call becomes automatically activated without appending any extra menus, reducing menu-bar switching across the entire application's lifecycle to one line of code per transition (e.g., MENU BAR(3) when showing a list, MENU BAR(4) on load of a detail form). The note also covers a real-world extension -- creating separate sets of menu bars per user role for permission-based menu differences -- and explains 4D's automatic "connected menu" behavior for the File and Edit menus that makes the empty menu bar behave as truly empty in practice.
