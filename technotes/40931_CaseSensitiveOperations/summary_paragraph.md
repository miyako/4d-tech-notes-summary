This Technical Note by David Adams tackles the fact that the 4th Dimension language and database engine of the era treat upper/lower case and diacritically marked variants of a letter (e.g., e, é, E, É, Ë) as equal, which is often convenient but becomes a real problem in scenarios requiring strict case-sensitivity, such as validating names, matching paths on case-sensitive volumes, and — most emphasized — comparing XML element and attribute names, since the XML specification mandates that element/attribute names are always case-sensitive regardless of 4D's native behavior. The accompanying sample database provides code for comparing alpha/text values and arrays case-sensitively, finding and counting values in case-sensitive text arrays, comparing BLOBs exactly, and accelerating case-sensitive text searches using either an optimized QUERY BY FORMULA replacement or the stored-hash technique from the companion HashTools component (documented in TN 05-43 and TN 05-44). It introduces a "speed mode" parameter supported by the pointer-based comparison routines, explaining that the performance trade-off between the faster and slower modes only becomes meaningful with larger data samples, and recommends testing compiled for accurate performance measurement. The note is explicitly positioned as part of a cluster of related notes (TN 05-42 on efficient text/BLOB scanning, TN 05-43 on the HashTools component, and TN 05-44 on hash-optimized searching), reflecting a broader technical-note initiative addressing 4D's engine-level text-handling limitations as XML and web-service integration became increasingly important to 4D developers in this period.
