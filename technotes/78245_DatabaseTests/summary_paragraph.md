This Tech Note addresses how to automate unit testing of a 4D database — launching it in different modes (single-user, client-server) across Mac and Windows — using a new "User parameter" feature introduced in v17R3, accessible through the SET DATABASE PARAMETER and GET DATABASE PARAMETER commands with the User param value selector. Before this feature, developers wanting mode-determination at startup had to resort to workarounds like writing marker text files for 4D to detect on launch; the User parameter formalizes this into a first-class, persistent value survivable across OPEN DATABASE, OPEN DATA FILE, and RESTART 4D calls. The note details three ways to set this parameter: directly in code as text or a JSON-stringified 4D object; via the command line using --user-param followed by text (including inline JSON-like object syntax, differing quoting between Windows and Mac); and via a .4DLink file's user_param="..." XML attribute for client connections, which can also be opened directly from the command line. Retrieving it is done with GET DATABASE PARAMETER, and because there's no built-in flag distinguishing plain text from a serialized 4D object, the note provides a CHECK_MALFORMED_JSON helper method (using ON ERR CALL around JSON Parse) to safely detect and parse object-typed parameters. The note closes with three general testing strategy ideas: simple standalone testing keyed off the parameter in On Startup, a repeat-based standalone testing loop that uses RESTART 4D to chain through a sequence of tests via a Case statement, and testing 4D clients via a customized .4DLink file. It's positioned as an enabling building block rather than a full test framework, aimed at developers and QA teams building custom automated test harnesses around 4D.
