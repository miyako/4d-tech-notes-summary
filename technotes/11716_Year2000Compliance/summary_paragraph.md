Written in 1996 as the software industry was beginning to seriously grapple with the looming Year 2000 problem, this Tech Note reassures 4D developers that 4th Dimension's internal Date data type is fundamentally Year 2000-safe: dates are stored internally with a full four-digit year rather than a truncated two-digit representation, so the underlying engine does not suffer the classic Y2K rollover bug. The practical risk it identifies instead lies at the user-interface and data-entry level: many database applications, following common conventions of the era, let users type only a two-digit year (e.g., "96" for 1996), and naive assumptions about which century that year belongs to can produce incorrect dates once the year 2000 arrives (e.g., "01" being misinterpreted as 1901 instead of 2001). To address this, the note presents a "pivot year" algorithm: a configurable threshold year below which two-digit input is assumed to belong to the 2000s and above which it's assumed to belong to the 1900s (e.g., with a pivot of 30, "29" resolves to 2029 while "30" resolves to 1930), and shows how to implement this logic in 4D method code applied to user-entered dates. It also documents the Sys date format command, which returns the current operating system's locale-specific date format string (revealing separator characters and field order), enabling developers to build locale-aware date parsing/validation routines, alongside the SET DATE FORMAT command for overriding 4D's own date display format when needed. Featured technology is 4D's Date data type together with the Sys date format and SET DATE FORMAT commands, applied specifically to solving the two-digit-year ambiguity problem ahead of the year 2000.
