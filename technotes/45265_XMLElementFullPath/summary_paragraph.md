This Technical Note by David Adams explains how to compute the full hierarchical path to an XML node using 4th Dimension's built-in DOM commands, addressing the common XML challenge that repeated element names (e.g., multiple <phone>/<area_code>/<number> elements nested under different parents like <business> and <home>) make it necessary to know a node's full path to unambiguously identify it. The note notes that 4D's native DOM Find XML element command can locate a node given a known path, but this is insufficient for two common scenarios: generic top-down tree-walking algorithms (used throughout other 4D XML tech notes and in "The 4D Web Services Companion") that process nodes from the bottom up without a known path in advance, and situations requiring pattern matching that DOM Find XML element's path syntax cannot express, such as matching any node ending in "/phone/area_code/" regardless of its ancestors. To solve this, the note documents a DOM_GetFullPath routine that starts at a given node, repeatedly calls DOM Get parent XML element to walk upward, and prepends each ancestor's name to build a "/element1/element2/.../" style path string, stopping and returning an empty string if the reference is null or invalid, and correctly excluding the synthetic "#document" node from the resulting path. The routine uses the same custom ON ERR CALL error-trapping pattern seen in companion XML tech notes to avoid crashing on invalid references, restoring the prior error handler and Error variable state afterward. A note flags that XML paths, element names, and attribute names are case-sensitive, cross-referencing Tech Note 05-41 for case-sensitive string comparison utilities. The sample database includes a Test_GetFullPath harness that exercises the routine against valid, invalid, and #document node references. The featured technology throughout is 4D's classic DOM XML API combined with a reusable path-building tree-traversal technique.
