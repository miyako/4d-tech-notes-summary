This tech note addresses a practical gap in 4D's data export/import tooling: both the built-in GUI and the EXPORT DATA/IMPORT DATA commands operate on a single table at a time, making a full-database export/reimport (useful for archival, backup, disaster recovery, troubleshooting, or migration) tediously manual for databases with many tables. The provided component exposes one entry-point method, export_import_all, that prompts for export vs. import via CONFIRM, a destination/source folder via SELECT FOLDER, and a format choice between XML (text, human-readable/editable) and 4D (binary), then loops over every valid table (Get last table number, Is table number valid) calling a helper method, export_import_one_table, for each. That helper builds a DOM-based XML "project definition" describing the table number, format, and every valid field via DOM Create XML Ref and DOM Create XML element, then calls EXPORT DATA or IMPORT DATA with that XML descriptor; on import it first TRUNCATE TABLEs the destination before importing to guarantee a clean reload. Before importing, the main method also disables indexes, constraints, and triggers via SQL's ALTER DATABASE DISABLE INDEXES/CONSTRAINTS/TRIGGERS, which requires Journaling to be turned off beforehand (otherwise an error occurs) — the note explicitly recommends disabling the Log ("Use Log") setting and commenting out STARTUP stored procedures before running the operation. A key side benefit called out is that exporting to XML text format exposes the full literal record content in a readable/editable form, useful for spotting and cleaning problematic control characters that could otherwise cause import errors — foreshadowing a planned follow-up tech note on data sanitization.
