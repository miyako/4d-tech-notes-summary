This Technical Note by David Adams addresses a core limitation of 4th Dimension's database engine of the era: it could not natively search strings case-sensitively, search text fields completely, or search BLOBs, pictures, or documents at all, and shows how hashing — reducing a block of data to a single longint — can optimize these operations. Delivered alongside the companion HashTools component (documented separately in TN 05-43), the note explains and benchmarks eight adapted C hashing algorithms (AP, BKDR, DJB, ELF, JS, PJW, RS, SDBM) plus a simple SumBytes function included for comparison, evaluating each for hashing speed, collision rate, and resulting search-speed gains across multiple sample data sets via a demonstration database with dedicated hashing, speed-test, and collision-test screens. It concludes that the AP, BKDR, RS, and SDBM algorithms are functionally equivalent choices for most 4th Dimension projects. The note describes the HashTools_FindByHash routine, which performs an indexed search on a stored hash field to eliminate non-matching records before doing an exact value comparison on the remainder, dramatically speeding up searches on text, BLOB, and picture fields when a hash is pre-calculated and stored (a good candidate for maintenance via triggers). The note stresses that hashing is not a universal solution — it requires precomputing and maintaining stored hashes — but for the specific problems 4D's engine could not otherwise solve efficiently, it delivers substantial performance benefits, and points readers to companion notes on case-sensitive operations (TN 05-41), the HashTools component API (TN 05-43), and efficient text/BLOB scanning (TN 05-42) for deeper context.
