This Tech Note is Part 2 of a two-part series arguing that 4D developers should reconsider two "rules" of good relational database design — avoiding 4D's built-in relational lookups and normalizing data — when performance is at stake, particularly for databases used over a WAN or dial-up connection. It reprises the shared introduction from Part 1 about breaking conventional relational-design rules under performance pressure, then focuses specifically on Rule #2: avoiding 4D's built-in relational lookup mechanism. It lays out the disadvantages that typically drive developers to write custom lookups instead — synthetic primary keys are not human-searchable, the built-in lookup selection list is limited to two displayed fields, the choice list isn't sorted, there's no control over the lookup window's appearance, and users can't override an auto-assigned new primary key — but counters that the built-in lookup is significantly faster (often 100%+ faster) than any custom routine, requires far less code, and is easier to maintain. The note then presents a concrete implementation technique to get the built-in lookup's speed while working around its limitations: create a dedicated [Lookups] file with alpha "relational connector" fields; add a concatenated Wildcard_Choice field to each "One" file, padded to fixed-width columns via a StringPadSpaces-style procedure so multiple pieces of information display as neat columns; place the lookup field on the appropriate input layout with Automatic Relate one and Auto wildcard support enabled; and set the Structure Font (via 4D Customizer Plus) to a monospaced font like Monaco or Courier so the padded columns align visually in the lookup Selection window. A companion example database ("Performance Rules") demonstrates Company, Contact, and Product lookups built this way. The featured technology is 4D's native relational lookup feature, its wildcard/auto-relate options, and the structure-font customization workflow needed to make concatenated multi-field lookup lists readable.
