This Technical Note by David Adams documents a significant behavioral change in the 4th Dimension 2004 Web Server: for the first time, developers gained complete freedom over how URLs submitted to the server were named, rather than being forced to prefix them with the special 4DACTION, 4DCGI, or 4DMETHOD keywords. Prior to this change, POST-submitted form data was stripped out of all three places it could otherwise appear — the On Web Authentication database method's $2 parameter, the On Web Connection database method's $2 parameter, and arrays populated by GET WEB FORM VARIABLES — unless the request URL began with one of those reserved keywords, with no available workaround. The note explains that each of the three special keywords triggers a slightly different processing sequence (running a Compiler_Web method, On Web Authentication, and either the named 4DACTION method or On Web Connection/4DMETHOD contextual execution), and that unknown/custom URLs already followed the same processing path as 4DCGI requests in both 4D 2003 and 2004 — the only difference in 2004 being that POST data is now actually available for such custom URLs. Practically, this meant developers could adopt arbitrary, policy- or brand-friendly URL structures (like /cgi-bin/process_form.php or /forms/search/) while still reliably retrieving submitted form values, most conveniently by calling GET WEB FORM VARIABLES once inside On Web Authentication and storing the results in process arrays for later use. The note is a focused, technical explanation of a Web Server internals change rather than a broad feature tour, aimed at developers who wanted cleaner or more flexible URL schemes for their 4D-hosted web forms.
