Josh Fletcher's Tech Note addresses a subtle but consequential change introduced in 4D v11 SQL: address tables (the internal structures mapping record numbers to disk locations) are no longer compacted automatically as part of a database Compact via the Maintenance and Security Center, a deliberate change made to preserve record numbers across compacts. The note explains the basics of address tables, record numbers, deletion, and compacting, then details why large, mostly-empty address tables can still hurt memory usage and performance even though they're no longer auto-compacted. It presents TRUNCATE TABLE as the solution, contrasts database-level compaction with address-table-level compaction, and walks through the challenges of doing this safely — triggers, referential integrity, indexes, table attributes, sequence numbers, and external vs. host database storage. The included AddressTableCompactor component automates the process, with recommended preparation, usage guidance, and suggested enhancements such as preserving/restoring indexes and sequence numbers around the operation.
