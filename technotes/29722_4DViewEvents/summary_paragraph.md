Gou Yang of 4D Technical Support explains how to make a 4D View spreadsheet-style grid area respond to user interaction and menu commands, since -- unlike ordinary form objects -- 4D View events are not wired up through the object property list's event checkboxes but must instead be installed programmatically. The note documents PV ON EVENT(Area;Event;Method), which attaches a named 4D method to one of eleven event constants (On Active Cell Changed, On Cell Value Changed, On Clicked, On Double Clicked, On Drag, On Drop, On Getting Focus, On Keyboard, On Losing Focus, On Right Clicked, On Scrolled, On Selection Changed), clarifying the sometimes-confusing distinction between On Active Cell Changed (fires whenever the current cell changes, even within an existing multi-cell selection) and On Selection Changed (fires only when the selected range itself changes). It shows the required $0-$6 parameter declarations event methods must include when compiled, including the column/row/key-modifier/ASCII-code parameters passed in. The second half covers PV ON COMMAND(Area;Command;Method), used to intercept and override standard menu commands (File > New/Open/Save/Save As) so that, instead of the default behavior of loading/saving 4D View documents as external files, the example replaces those commands with methods that store and retrieve the 4D View area's contents as a BLOB in a [zDialogs] table record via PV Area to blob and PV BLOB TO AREA -- keeping documents entirely inside the 4D database.
