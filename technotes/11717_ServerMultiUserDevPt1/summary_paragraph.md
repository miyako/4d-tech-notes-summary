This Tech Note by Walt Nelson is Part 1 of a three-part series on developing with 4D Server, continuing a broader run of notes on 4D's built-in features (following earlier notes on subfiles/relational lookups and Choice Lists), and it argues for the advantages of developing with 4D Client connected to 4D Server rather than in traditional single-user 4th Dimension. It opens by cataloging familiar pain points of single-user development: losing track of which copy of a structure (home vs. office) is current, font/rendering differences between Mac-created and Windows-run layouts, merge headaches when multiple developers work on the same code, and documentation screenshots that render inconsistently across platforms. It then honestly discusses the disadvantages of Server-based development first: needing a server machine and user licenses (though a modest machine suffices, with only additional RAM as the real cost); reduced speed over remote connections (roughly 10x slower to sign on remotely versus local Ethernet, though local-machine speed resumes once an object is copied down); distracting periodic Structure Window refresh "flashing" on 4D Client (mitigated by shrinking the window); and compiling, for which it recommends installing Timbuktu Remote on both server and client so a developer can remotely control the server machine and run 4D Compiler at full local speed, then copy the compiler's output files (Error log, Symbol table, Type file) to each client. It then details the advantages, which it argues far outweigh the downsides: Simplicity (a single "Current Development Version" folder on the Server eliminates version confusion across office/home/travel); Hard drive space (avoids redundant large data files on multiple local machines, since the shared data file lives once on the Server); Realistic performance measurement (developers on fast machines get an unrealistically rosy view of performance; testing over a remote connection to a Server approximates real-world customer conditions — "if it performs OK over a remote Quadra/486 connection, it will perform superbly on local Ethernet in an office"); Multi-platform testing (immediate cross-platform verification of forms/reports on connected Mac and Windows clients without the older Transport-structure-back-and-forth workflow); and Multi-programmer development (the single biggest advantage — many developers working from one shared code base, avoiding painful manual merges), with three caveats: 4D's object-locking model requires developers to close layouts/procedures promptly so others can access them; developers must respect others' code to avoid inadvertently "breaking" shared routines (a problem Part 2 addresses via modular password permissions); and window title bars can be pushed off-screen when moving between platforms, requiring specific keyboard-plus-mouse combinations (Command+Control+Click+Drag on Mac, Control+Right-Mouse+Click+Drag on Windows) to recover them. Finally, it notes that using 4D Write as the shared documentation tool lets developers paste in both Mac and Windows screenshots into the same shared document/record for genuinely cross-platform documentation. The note closes by previewing that Part 2 will cover setting up a multi-developer password system and Part 3 will cover naming conventions for multi-developer projects. As an argument for centralized, server-based multi-developer workflows, most of its reasoning about eliminating version confusion, enabling realistic performance testing, and supporting concurrent multi-programmer/multi-platform development remains sound today, even though specific tools it names (Timbuktu Remote for remote compiling, era-appropriate hardware comparisons, and 4D Write as the shared documentation vehicle) are now dated or superseded.
