This Tech Note tackles a subtle but important architectural question: how form data scoping and update propagation work between parent forms and subforms once a developer adopts ORDA's fully object-oriented design (where a form can be built entirely from JSON-defined objects, with no process variables). It clarifies that a parent form has read/write access to its own data and its subform's data, while a subform can only see its own data — a strictly top-down visibility model — and walks through the precise event order (Event 1: DIALOG passes form data to the parent before any On Load fires; Event 2: subform On Load; Event 3: subform container On Load; Event 4: parent form On Load), emphasizing that initializing Form.Subform1 as a New object during the DIALOG call (rather than only in On Load) avoids a null-reference error when the form is launched via the "green triangle" execute-method button instead of a wrapping open-form method. A key gotcha covered is that reassigning Form.Subform1 to a fresh object after the fact requires calling OBJECT SET SUBFORM to force the listbox to pick up the new reference — except starting in v17R6, where this call is no longer necessary because entity/collection-based list boxes auto-refresh their reference. For bidirectional updates, the note shows the parent freely writing to Form.Subform1.LB directly (with EXECUTE METHOD IN SUBFORM needed only when a specific widget/action must run inside the subform's own context), and the reverse direction — subform-to-parent — requiring CALL SUBFORM CONTAINER with a negative (or >59) event number to signal the parent's subform container method, since a subform has no visibility into parent data by itself. The note closes by framing all of this as encouragement to embrace 4D's ongoing shift toward a fully object-oriented programming mindset.
