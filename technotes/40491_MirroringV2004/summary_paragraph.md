This Technical Note by Kent Wilbur introduces two new language commands added in 4D 2004.3 that enable building a database mirroring system — maintaining a second, identical database running in parallel to the active one so that, in the event of failure, the mirror can be promoted to primary within minutes without a full restore from backup. It explains that mirroring is built around the log file mechanism: an initial backup and log file are transferred to the mirror machine to create matching originals, after which the New log file function periodically closes, renames, and creates a new segmented log file (numbered like MyDatabase[0739-0001].4BL) on the primary server, and the INTEGRATE LOG FILE command applies each transferred segment on the mirror. Unlike pre-2004 mirroring (which required near-identical hardware and operating systems), 4D 2004.3 mirroring can operate cross-platform, with the only strict requirement being that the mirror machine never independently modifies data. The note candidly notes it is an introduction to the new commands rather than a turnkey solution, since developers must adapt it to their own requirements, and it demonstrates transferring closed log segments to the mirror server using a 4D SOAP call (chosen for its simplicity and built-in success/failure reporting) alongside custom Client-Server communication for remotely modifying mirroring preference settings stored in an XML file. This combination of new mirroring commands, log-segment transfer, and XML-based preference management illustrates the sophisticated, DIY-oriented approach 4D developers took toward high-availability database design in the mid-2000s, before more automated mirroring/HA features existed.
