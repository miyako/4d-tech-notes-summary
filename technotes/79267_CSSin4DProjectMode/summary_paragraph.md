This technical note documents the CSS-based external style sheet feature that project-mode 4D databases gained over binary mode's much more limited style sheets, which could only configure font, size, and style per platform for text elements. In project mode, three default files — styleSheets.css (cross-platform), styleSheets_mac.css, and styleSheets_windows.css — live in the Sources folder (created via the Toolbox's Style Sheets page) and can style nearly any form-element property using CSS2 syntax; converting a binary database to project mode automatically translates its old style sheets into platform-specific CSS classes attached to each form element's new CSS Class property. The note catalogs 4D's five selector types — object type (matching the JSON-equivalent "Type" value, e.g. "webArea"), object name (an ID-style "#name" selector), class (".className", supporting multiple space-separated classes per element), the universal "*" selector, and four supported attribute selectors ([attribute], [attribute=value], [attribute~=value], [attribute|=value]) — along with a selector-type precedence order where more specific selectors (e.g., class) override more general ones (e.g., object type) when rules clash. It covers CSS declarations as JSON-named property/value pairs (cross-referencing 4D's online properties reference), 4D's built-in CSS color-constant strings (e.g., "orchid" for #DA70D6) as a convenience over hex/RGB values, and the currently sole supported media query, `@media (prefers-color-scheme: light|dark)`, for automatically theming forms differently under macOS light/dark mode. Beyond the three default files, the note explains two modularization techniques for larger projects: `@import` statements (with relative-path conventions using "/" for child folders and "../" for parent folders) to split CSS into reusable partial files that still get merged into the main stylesheet at runtime, and a community-discovered "dynamic" per-form stylesheet workaround (credited to 4D VP of Strategy Thomas Maul) that attaches an individual CSS file to a specific .4DForm via a JSON pointer (`"css": {"$ref": "/RESOURCES/theme.json#/css1"}`) referencing a directory JSON file in the Resources folder, with the actual CSS stored in the client/server-writable Logs folder — enabling per-user or per-client themes, though incompatible with the live CSS Preview feature in the Form Editor. Finally, it lays out the overall style-sheet precedence hierarchy — dynamic style sheets, then form definition properties, then `!important`-tagged CSS rules, then the platform-specific default file, then the general styleSheets.css — giving developers a coherent model for predicting which style wins when multiple sources conflict.
