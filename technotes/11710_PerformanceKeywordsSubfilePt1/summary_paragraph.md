This Tech Note, Part 1 of a two-part series, argues that developers should be willing to break two classic relational-design "rules" — avoiding subfiles and avoiding data duplication/denormalization — when a database's search performance suffers over a WAN or dial-up connection. It opens by describing standard "Quick Search" interfaces as problematic for remote users: they require knowledge of the data's structure, mouse-driven field selection, tolerance for inconsistent naming/spelling, and expanding UI/code for multi-field searches — all of which become far more costly (a 7-second local search becoming 70+ seconds over a modem) as network latency increases. The proposed solution expands the traditional 4D "Keywords subfile" pattern (normally used just to tag records with categories) into a general-purpose, single-index search mechanism: create a Keywords subfile with one indexed alpha field; write a parsing routine that splits any target string into individual words; write a routine that creates a keyword subrecord for each unique word if it doesn't already exist; wire these routines into the data-entry scripts of every field the user might want to search (contact name, company, case number, product, etc.); and build an Included Output Layout with a single enterable "vFind" variable that lets the user type free-text keywords and get matching parent records back — supporting special characters like `&` (AND-match) and `_` (phrase match) for power users, and allowing user-defined keywords for personal record retrieval. The note enumerates nine advantages of this approach (no need to know data structure, single field to type into, tolerance for spelling variance, no expanding UI for multi-field searches, and consistently fast performance since the keyword index stays cached), while cautioning that subfiles should be limited to one short field (~30 characters) and roughly 25-30 subrecords per parent, since 4D sends entire records with subrecords to the client. Featured technology centers on 4D subfiles used as a search index, plus array/string parsing procedures and Included Output Layouts with enterable search variables.
