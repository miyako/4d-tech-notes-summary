This Technical Note addresses a critical migration concern for developers converting legacy 4D databases to 4D v11 SQL: subtables, a data structure supported in prior 4D versions, no longer exist as a creatable structure in v11 SQL, and the conversion path differs sharply depending on whether a database uses single-level or multi-level (nested) subtables. For single-level subtables (a subtable directly owned by a "real" 4D table), 4D v11 SQL automatically converts them into standard related tables during database conversion, adding a new foreign-key field (named with an "id_added_by_converter" pattern) and a special, non-recreatable many-to-one relation that preserves backward compatibility so existing subtable-oriented code continues to function, while the note recommends that developers eventually rewrite this code to use standard related-table techniques instead. It flags several behavioral differences post-conversion that developers must account for: the total table count increases (e.g., 10 tables plus 2 subtables becomes 12 standard tables), subrecords are no longer auto-loaded with their parent record (since they are now genuinely separate related records), and the RECEIVE RECORD command supports importing legacy multi-version formats while the v11 SQL SEND RECORD command no longer exports subrecords at all and produces a new record format incompatible with pre-v11 4D installations. For multi-level subtables (subtables nested inside other subtables), the note is stark: conversion is not supported whatsoever, and any data in subtables beyond the first level is simply lost upon conversion to 4D v11 SQL, making pre-conversion data extraction mandatory. To help developers who relied on SEND RECORD/RECEIVE RECORD for database synchronization (which the new SEND RECORD's dropped subrecord support breaks), the note references and bundles a community-authored, open-source component ("SendReceiveRecord.4dbase," created by Thomas Maul of 4D Germany) that provides replacement synchronization methods compatible with the special subtable relation. As a practical, one-time migration document tied specifically to the very significant 4D v11 SQL structural changes, it captures a transitional pain point developers faced when adopting 4D's new SQL-native architecture.
