Written by Eric Saltzen of 4D, Inc. Technical Support, this Tech Note explains how HTTP cookies work at the protocol level — the `Set-Cookie:`/`Cookie:` header exchange, per-domain/path scope, and where different browsers of the era stored cookie files (MagicCookie on Mac Netscape, cookies.txt on Windows, etc.) — and then builds a complete visitor-tracking sample database, "CookieMonster4D," to demonstrate the technique end to end. The database's single On Web Connection method inspects the requested URL ($1) in a Case statement, and for recognized site pages calls a hand-written ParseCookies project method that manually walks the raw HTTP header text (using Position, Substring, and array insertion) to extract cookie name/value pairs, since 4D at the time had no built-in cookie parser. If no "primaryID" cookie is found or it doesn't match any [WebVisitors] record, the code generates a guaranteed-unique 32-bit ID from the current date/time in seconds since Jan 1, 2000 plus centiseconds from Milliseconds, re-checking for collisions in a Repeat loop; it then creates a [WebVisitors] record, issues the new cookie via `SET HTTP HEADER("Set-Cookie: primaryID=...; expires=...; path=/")`, and serves an introductory index.htm page (built with 4DVAR template tags) asking the visitor to enter their name. On a returning visit (or after form submission to "/4DCGI/AssignName"), the matching [WebVisitors] record is updated and the personalized home.shtm page — built with Macromedia Dreamweaver/Flash and 4DVAR/4DCGI placeholders — is served via SEND HTML FILE, while a separate Case branch in the same method uses SEND HTML BLOB to serve inline images referenced from /4DCGI-processed pages. The note positions this as a practical worked example of session/state management for a 4D-served website using only the raw HTTP header and hand-written parsing code.
