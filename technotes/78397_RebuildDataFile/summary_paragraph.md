This tech note offers a clever, defensive maintenance technique: rebuilding a fresh, uncorrupted datafile from an existing one by repurposing 4D Server's mirroring/journaling infrastructure, rather than restoring from a full backup or performing risky low-level repairs. The procedure works by creating a new, empty journal (log) file via `New log file`, then loading and re-saving every record of every selected table (`ALL RECORDS`/`NEXT RECORD` plus a re-save) so each record generates an update event that lands in the fresh journal — effectively capturing a complete, current snapshot of the chosen tables' data as a sequence of mirror events. The note flags a known caveat: Picture and Blob fields are only journaled when specifically modified, so those fields must be explicitly reassigned (using `GET FIELD PROPERTIES` to detect them) to force their inclusion. Once the journal captures all desired data, `CREATE DATA FILE` spins up a brand-new empty datafile and restarts the database against it, after which `INTEGRATE MIRROR LOG FILE` (run with auto-repair mode, since no pre-existing records exist to update) replays the journal to populate the new datafile — automatically compacting storage and clearing any underlying corruption tied to old references or headers. A provided sample "Data File Reconstruction" component wraps this in a UI: a table-selection list box (to optionally exclude tables), a "Generate Logs" step with options for automatic rebuild-on-restart or per-table separate journals (enabling parallelized, preemptive processing), and an "Integrate Logs" step for manually selecting which journal files to replay. This technique is positioned as both a corruption-recovery tool and an incidental size-reduction/compaction utility, requiring 4D Server and full understanding of the mirroring feature it repurposes.
