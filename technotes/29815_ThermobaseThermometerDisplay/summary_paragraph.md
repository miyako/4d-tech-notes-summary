This Tech Note by Jean-Yves Fock-Hoon, QA Manager at 4D, Inc., works through the classic 4D UI problem of displaying a progress bar for a lengthy task: because a busy process only services window redraws when it idles waiting for an interface event, a thermometer object living in the same process as the long task simply never updates on screen. The solution demonstrated is to launch a second, dedicated process whose only job is to own and redraw the thermometer dialog, while the working process periodically pushes new progress values into it using a global variable, updated across processes with VARIABLE TO VARIABLE or SET PROCESS VARIABLE. The M_Thermo_Create/M_Thermo_Display/M_Thermo_Update/M_Thermo_CloseBox method set implements a single reusable thermometer dialog: the thermometer object itself is set non-enterable (since it's editable by default and the user could otherwise drag it), and the dialog is refreshed either via an On Timer event (redrawing every 60 ticks — noted as wasteful if the value rarely changes) or on demand by having the working process call CALL PROCESS to trigger an On Outside call event, which the author identifies as the better approach. A four-system M_Thermo_Create parameter selects between using the native Thermometer object or a scaling picture (useful for custom thermometer artwork), each combined with either the On Timer or On Outside call update strategy. A second example, M_ThermoMulti_*, extends the pattern to show up to five simultaneous progress bars stacked in one resizable dialog window, using two synchronized interprocess arrays (message text and current value per slot, with -1 marking a free slot) so several concurrently running tasks can each claim and release a row in the shared thermometer window rather than opening a separate process/window per task. The note closes by cautioning that blindly issuing SET PROCESS VARIABLE / CALL PROCESS against an arbitrary process number is risky and developers must verify they're targeting the correct process.
