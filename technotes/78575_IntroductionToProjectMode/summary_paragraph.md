Written as 4D's Project mode was still a relatively new architecture (introduced starting v17 R5), this note provides a foundational tour of what changes when a database moves from the traditional binary (.4DB) format to a Project. It shows creating a new project via "File > New > Database Project…" or converting an existing binary database via "File > Export > Structure to project…", which generates a `.4DProject` folder alongside the original `.4DB` and produces JSON conversion logs classified into Info, Warning, and Error severities. The bulk of the note walks the resulting folder structure: the Explorer's Home, Tables, Forms, Methods, and Trash sections now map directly onto files on disk — table/field definitions live in an XML `catalog.4DCatalog`, forms are split into Project Forms and Table Forms stored as `.4DForm` files (including embedded 4D Write Pro zone properties), and methods (project methods, database methods, triggers) are stored as individual `.4dm` text files retaining comments and an SQL flag if applicable. Deleted forms/methods move into a Trash folder rather than disappearing, and user/group definitions — previously stored inside the binary `.4db` — are extracted into a `directory.json` file, changing single-user-mode authentication behavior (the current user always defaults to "Designer" in mono mode; identification only matters in Client/Server). Menus become a `menu.json` file, the Picture Library is deprecated in favor of an exported picture folder in Resources, style sheets export as platform-specific CSS files, and user preferences (breakpoints, window positions, workspace) are stored per-user as JSON files. The note closes with a compact binary-vs-project comparison table, emphasizing that Project mode's plain-text format enables distributed teams to use source control tools, track change history/authorship, and roll back destabilizing changes — capabilities the older binary, 4D-Server-hosted development model didn't offer.
