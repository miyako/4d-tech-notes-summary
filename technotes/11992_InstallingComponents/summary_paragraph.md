In this Tech Note, Steve Hartman of 4D, Inc. Technical Support walks through the full process of creating and installing a 4D v6.7 component using 4D Insider, from building a library and marking objects Public, Protected, or Private through generating the component file and installing/updating it into a target database. He explains the practical implications of each visibility level (Protected methods can be called but not inspected or edited; Private objects are invisible to component users; tables, fields, and menu bars can never be marked Private), and gives concrete recommendations for avoiding naming conflicts, including using a unique developer/company prefix on all module objects, typing objects with compiler directives, and using the Get Module Resource ID function to manage STR# and PICT resources. The note also covers operational quirks such as Insider's conflict log during installation, the requirement that a component needing a table must also include a form for it (and vice versa), and the fact that tables, fields, menu bars, picture libraries, and lists are left behind when a component is uninstalled. A worked example, a "Parrots" database that computes inoculation-age statistics for parrot demographics, is built, packaged into a component, and installed into a fresh database to demonstrate that the resulting database behaves identically to the original. The overall purpose is to let developers deploy protected, independently updatable pieces of application code without exposing method source to end users while retaining the ability to revise and redistribute that code as a self-contained unit.
