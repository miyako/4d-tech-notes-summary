This Tech Note demonstrates how to build a complete numeric-PIN authentication system in a 4D application, positioned as a replacement for, supplement to, or additional gate on top of 4D's default password system. The interface consists of a keypad form with a status message area, a visual input indicator (a row of shape objects shaded per digit entered), numeric buttons, and a backspace button. PIN validation is implemented by looking up the currently authenticated user (via the `Current user` command) in a `user` table (`ds.user.query("username =:1";$user).first()`) and comparing the entered PIN against the stored hash using `Verify password hash`. Successful validation displays a success message and calls `ACCEPT` to grant access; failed validation clears the input indicators, displays an error message, and shakes the form via a custom method for visual feedback. The note also covers first-run PIN registration: on startup, the app checks whether the current user exists in the `user` table, and if not, sets a `Form.setuppin` flag that prompts the user to enter and re-enter a new PIN, comparing the two entries before calling a `setup_pin` method that hashes the value with `Generate password hash` and either creates a new `ds.user` entity (using `GET USER LIST` to resolve the corresponding 4D user ID) or updates an existing one — the same method doubling as the "change PIN" flow. Critically, the note stresses that PINs must always be stored hashed, never in plain text. The included demo ships with a default "Designer" account pre-registered with PIN "1111," and explains how a real deployment could extend the pattern to let users pick which account to authenticate as, rather than relying solely on the platform's `Current user`.
