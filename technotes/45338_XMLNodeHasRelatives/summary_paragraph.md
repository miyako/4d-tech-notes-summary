This Technical Note by David Adams addresses a gap in 4th Dimension's native DOM XML command set: there is no built-in way to test whether a given XML node has ancestors, children, or siblings, information that's commonly needed for tasks like generic top-down tree-walking algorithms, custom XML import routines, or visually distinguishing nodes (e.g., bolding list items that have children) when displaying XML hierarchically. The note provides three utility routines — DOM_NodeHasChildren, DOM_NodeHasAncestors, and DOM_NodeHasSiblings — each of which attempts to navigate to a related node (via DOM Get first child XML element, DOM Get parent XML element, or DOM Get previous/next sibling XML element) and reports success or failure as a boolean, defaulting to False on any invalid reference. DOM_NodeHasAncestors specifically treats the synthetic "#document" node (an artificial node above the true tree root holding document-level info like version/encoding) as not a true ancestor, since naive testing would otherwise misreport the root element as having a parent. All three routines rely on a shared DOM_ReferenceIsValid helper (adapted from an earlier Tech Note #06-40) plus DOM_StartCustomErrorHandling/DOM_StopCustomErrorHandling routines that install and restore a custom ON ERR CALL error handler so that attempts to read invalid node references don't crash or interrupt program flow. The accompanying sample database includes a Test_NodeHasRelatives routine exercising all three functions against good nodes, bad nodes, and the #document node, displaying pass/fail alerts for each case. The featured technology is entirely 4D's classic DOM XML command suite along with the note's custom defensive-programming pattern for safely probing tree relationships without triggering runtime errors.
