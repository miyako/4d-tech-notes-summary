Since 4D 20 R4, the EXPORT STRUCTURE command can output a database's structure definition as HTML in addition to XML, and this technical note shows how to turn that HTML into a queryable, programmatic asset. The HTML is organized in predictable, repeating patterns — each table gets a section marked by a "[ - ]" toggle label, followed by up to five sub-tables (Table Info, Triggers, Fields, Many-to-One, One-to-Many) whose values sit inside `<td>` cells, with `<img>` tags representing boolean true values. The note walks through writing a `parseStructDefHTML` method that traverses this markup and reduces it into a normalized JSON object containing collections of tables (each with info, triggers, fields, and relations) as well as a flattened "all fields" collection. On top of that JSON model, a `StructDef` class is introduced whose constructor stores the parsed object and whose functions — `findFields`, `findTables`, and `findRelations` — iterate the collections to answer queries like "which fields use Cluster B-tree indexing?" or "which tables are excluded from the log file?" by matching a given property/value pair. The author contrasts this HTML-based approach favorably against XML parsing (no XPath needed, more consistent property coverage) and against the structure editor or datastore inspection (broader property coverage including comments, triggers, and relations). A companion sample application, built to be installed as a component, demonstrates the full pipeline together with an `openStructDefFinder` form that lets developers search tables/fields/relations and drill into results via a list box. The overall contribution is a lightweight, reusable inspection/reporting tool that lets 4D developers programmatically audit their own database structure without manual XML/XPath work.
