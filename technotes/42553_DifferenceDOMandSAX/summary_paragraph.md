This Tech Note by Yvan Ayaay explains the conceptual and practical differences between 4D's two XML manipulation modes, DOM (Document Object Model) and SAX (Simple API for XML), assuming the reader already has a basic understanding of XML (pointing to the separate "XML: An Introduction" note for background). It frames the core tradeoff around memory usage and traversal style: DOM parses an entire XML document into an in-memory tree that can be navigated randomly in any direction (forward, backward, parent/sibling/child), making element access very fast but potentially memory-prohibitive for very large documents, whereas SAX processes a document as a one-way stream of events (start tag, end tag, data, etc.) from top to bottom without ever holding the whole structure in memory, making it scale to arbitrarily large documents but restricting documents to read-only, linear access with no modification support. The note gives concrete guidance for choosing between them: DOM suits smaller files or scenarios requiring random/complex data access, while SAX suits very large files or scenarios where data only needs to be extracted once in sequence; ultimately it acknowledges the choice can also come down to programming style preference. It then demonstrates creating an identical XML document (a list of people's names with title attributes) using each approach: the DOM example builds an in-memory tree via `DOM Create XML Ref`, `DOM Create XML element`, and `DOM SET XML ELEMENT VALUE`, using stored element references to attach children and siblings before finally calling `DOM EXPORT TO FILE`, while the SAX example creates a document reference via `Create document`/`SAX SET XML OPTIONS` and issues a strict, order-dependent sequence of `SAX OPEN XML ELEMENT` / `SAX ADD XML ELEMENT VALUE` / `SAX CLOSE XML ELEMENT` calls that must be manually balanced to produce a well-formed hierarchy, ending with `CLOSE DOCUMENT`. It similarly contrasts parsing/traversal: DOM opens a document with `DOM Parse XML source`, then locates and walks elements using commands like `DOM Find XML element`, `DOM GET XML ELEMENT VALUE`, and `DOM Get Next sibling XML element`, optionally using XPath notation for direct addressing, while SAX opens a document in mandatory read-only mode via `Open document` (noting that 4D and the underlying Xerces library can conflict if a document is opened read-write during SAX parsing) and repeatedly calls `SAX Get XML node` in a loop, checking the returned event constant (e.g., XML Start Element, XML DATA, XML End Document) to drive a state machine that extracts element names and values via `SAX GET XML ELEMENT` and `SAX GET XML ELEMENT VALUE`. The note closes by reiterating that DOM trades memory for flexibility (full read/write modification support) while SAX trades flexibility for scalability (unlimited document size, no in-memory footprint), a distinction that remains standard, accurate guidance for anyone working with 4D's classic XML command set today.
