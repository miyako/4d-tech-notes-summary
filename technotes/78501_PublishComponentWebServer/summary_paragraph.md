Starting with 4D v18R3, a 4D application can run multiple independent Web Servers: one for the host database and one for each installed component, which lets developers publish web-based tools (such as a server monitoring dashboard) without conflicting with the host application's own web server. This tech note walks through adapting the "ServerAdmin" component (a downloadable web-based monitoring dialog from the 4D blog) so its bundled Web folder is served from its own dedicated HTTP server rather than the host database's. The core API is the new `WEB Server` command, which returns a read-only web server object exposing properties like `isRunning`, `HTTPPort`, `HTTPSPort`, `rootFolder`, and `maxSessions`, and which can target the current database, the host database, or the server that received the current request. Instantiation happens in the component's `On Host Database Event` method (which must be explicitly enabled by the host database for security), and the server is then controlled via member methods `.start()` and `.stop()`, with `.start()` accepting an options object to override port, HTTPS, and root-folder settings without touching the host database's own web preferences. The `WEB Server list` command returns a collection of all instantiated component/host web server objects, letting an admin discover and manage them collectively. The note includes a full example method that starts the ServerAdmin component's web server on port 8080 and shows the resulting admin UI reachable at `/admin/ini`. This pattern positions 4D components as self-contained, independently deployable web modules — useful for splitting large applications into separately servable pieces (e.g., an admin console) without needing separate 4D Server instances.
