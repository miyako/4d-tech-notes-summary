This Tech Note is a comprehensive reference on the 4D cache — the memory buffer that stores structural definitions, records, indexes, BLOBs, selections, sets, and other frequently accessed data to avoid slow disk access — tracing its evolution from the very limited Maximum Cache setting in 4D v6.0 through the Flush Data frequency introduced in 2003 to the modern adaptive cache and live-adjustable Cache size/flush frequency (via SET CACHE SIZE or the interface) available since 4D Server v16 (64-bit). It clarifies what is and isn't cached (e.g., the 4D Web Server cache and Storage content are held in memory but not the structural cache) and stresses key operational considerations like ACID compliance and the shifting CRUD balance as datasets grow, plus the default 400MB maximum cache size (50% of available RAM) that developers must manually increase for production deployments. The note catalogs every command available to introspect cache state: GET MEMORY STATISTICS (formerly GET/MEMORY CACHE STATISTICS) for general memory/cache sizing, Get database measures (since 4D v14.3) for detailed disk/cache read-write byte and access counts, Cache info (since v16) for a snapshot of currently loaded cache objects, Priority in Cache Set/Get for fine-tuning retention, and DataStoreClass.flushAndLock() for freezing the cache to a consistent state before snapshots. It also documents the Runtime Explorer, Administration window graphs, and the community-maintained 4D_Info_Report GitHub component for historical cache-usage reporting and load-test analysis, and closes by distinguishing the classic 4D engine cache from the separate ORDA remote cache — an expiring (30-second), dataclass-organized client-side cache controllable via dataClass.setRemoteCacheSettings/getRemoteCache/clearRemoteCache. Overall, the note serves as an update-oriented reference for administrators tuning cache size and diagnosing performance issues across current and recent 4D Server versions.
