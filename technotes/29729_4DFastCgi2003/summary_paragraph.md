Authored by David Adams, this note introduces the 4D FastCGI 2003 component, which lets 4D, 4D Client, or 4D Server act as a persistent FastCGI application behind high-performance Unix/Linux web servers such as Apache and Zeus. It positions FastCGI as solving the two chronic weaknesses of plain CGI (per-request process startup cost) and server-specific APIs like ISAPI/NSAPI/WSAPI (tight coupling to one web server), while remaining language-independent and able to run on any machine on the network for distributed processing. The note walks through the FastCGI request lifecycle -- browser to web server to the 4D FastCGI process and back -- and explains that FastCGI messages, while similar in spirit to HTTP, use their own binary-safe framing and are capped at roughly 65,000 bytes per message (larger payloads are chunked automatically by the component). A concrete code sample shows the core API in action: FCGI_Accept waits for and receives an incoming request, FCGIRequest_ValueGetByName reads request parameters like REQUEST_URI, FCGIResponse_SetContentType and FCGIResponse_AddBLOB build a binary response (in the example, a GIF logo converted with PICTURE TO GIF), and FCGI_Reply sends the response headers and body back through the web server. Installation is via 4D Insider, requires a compatible 4D Internet Commands plug-in, and full FastCGI request handling requires the 4D Extension License (WEL); without it, the component works for roughly one hour before requiring a restart.
