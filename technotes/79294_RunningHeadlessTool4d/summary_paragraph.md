This technical note introduces tool4d, a new command-line tool shipped starting with 4D v20 that opens a .4DB or .4DProject structure and executes 4D code entirely from a terminal or PowerShell prompt, without requiring a 4D license — making it well suited to unlicensed VMs, CI pipelines, or quick scripted operations like data export, print jobs, settings retrieval, or data verification. On launch, tool4d runs through the same lifecycle as a normal 4D app (On Startup, an assigned user Startup Method, an optional `--startup-method` argument, then On Exit) but with numerous features disabled by default for a lightweight footprint — application/web/SQL servers, the backup scheduler, ODBC, all components, spell checkers, WebAdmin, CEF, PHP, and the debugger — meaning only native 4D commands should be relied on since component calls are silently ignored. The note walks through downloading the correct tool4d build matching the target 4D version from product-download.4d.com, extracting it per-OS, and invoking it with the syntax `<tool4d path> <structure path> [args]`, covering commonly used arguments such as `--data`, `--create-data`, `--user-param`, `--dataless`, `--skip-onstartup`, and `--startup-method` (noting `--headless` has no effect since tool4d always runs headless). Because headless execution produces no visible output, the note recommends a cross-platform `logEvent` helper wrapping `LOG EVENT` (writing to Windows Event Viewer or, via `Into 4D debug message`, macOS Console) placed in On Startup/On Exit and throughout demo methods to confirm successful execution. A key pattern demonstrated is using `--user-param` together with `Get database parameter(User param value; $param)` inside a startup method to branch behavior via a `Case of` statement, letting one structure file support multiple scripted actions (export, settings, print, verify) selected purely from the command line. The accompanying demo database implements four such methods — `exportDataToText` (via `EXPORT TEXT` per table), `getSettings` (serializing `Get application info`/`Get system info`/log settings to JSON via `JSON Stringify`), `printTest` (via `PRINT SELECTION` with a PDF print destination, avoiding disabled component-based printing like WP PRINT), and `verifyDataFile` (via `VERIFY CURRENT DATA FILE`) — and running all four when no user parameter is supplied, positioning tool4d as a foundation for unit testing and CI/CD workflows referenced in 4D's blog for further examples.
