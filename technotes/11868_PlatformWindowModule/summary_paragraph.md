This Tech Note by Jeff Browning presents a fully reusable "window management module" for 4D 3.5 that abstracts away the platform-dependent quirks of opening and positioning windows on Macintosh versus Windows. It explains that under Windows, OPEN WINDOW positions windows relative to the top-left corner of the application (or MDI) window rather than the screen, complicating centering, and that 4D 3.5's new layout-scaling feature (for higher-resolution Windows displays) means a separate, appropriately-scaled layout must be loaded per platform "look." The module supports opening windows at many positions (center, upper/lower center, all four corners, stacked/cascaded, fill-screen, offscreen), across all standard 4D window types (modal variants, DA style, floating with/without scroll bar, and modeless variants), while transparently handling resizing, layout loading, and title assignment based on the current platform look (Automatic, Macintosh, Windows 3.1, Windows 95). A distinctive feature is transparent, cross-process window stacking/cascading, where closed bottom-most stacked windows free their position for reuse by new windows. The accompanying WinMod example database provides a Test Windows dialog letting a developer interactively exercise every position, type, size, title, and look option, and it even builds a corresponding line of 4D code that can be copied directly into the developer's own procedures. Core procedures documented include Startup_WI (initializes interprocess constants for window types/positions), WI_OpenStd (the main window-opening entry point), WI_CloseStd, and a WI_Layout helper for loading the correct scaled layout, plus a small generic ER_ErrorProc error-reporting helper used by both this and the companion platform-detection module. The module explicitly depends on a separate "Platform and Look Detection Module" (TN 96-20, also by Jeff Browning) and requires the ACI_PACK extension package bundled with 4D/4D Server of that era. The note demonstrates a disciplined engineering approach for its time — encapsulating platform quirks behind a single reusable interface, using a TE_-prefixed testing module convention, and favoring interprocess variables and parameter constants over hardcoded magic numbers. As a practical takeaway, it saved developers from writing ad hoc, error-prone platform-specific window-positioning code throughout their databases.
