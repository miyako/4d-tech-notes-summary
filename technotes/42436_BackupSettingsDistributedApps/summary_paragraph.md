This Tech Note by Jean-Yves Fock-Hoon addresses a common deployment pitfall for distributed 4D applications: developers typically test the Backup system on their development machine, which silently creates a Backup.XML project file recording (among other things) a backup destination folder path valid only on that machine. When the application is later built and moved to another machine — including as part of a merged 4D Server/Runtime build — that stale path is invalid, and 4D prompts the end user with a folder-selection dialog the first time a backup is attempted, which is often confusing or undesirable in a polished distributed application. The note first covers the simplest workaround (not copying the Backup.XML file at all, letting 4D silently regenerate one with default settings on first launch) but notes this doesn't allow the developer to specify custom backup settings such as archive retention count, extra files to include, performance tuning, or a specific backup schedule. It then presents two approaches for generating a custom Backup.XML with predefined settings: directly building the XML via 4D's native XML-parsing commands (noted as workable but brittle, since the XML-building code must be kept in sync if 4D's Backup.XML schema changes in a future version), and a preferred alternative of maintaining a Backup.XML2 template file, written with 4D HTML/merge tags standing in for values, that is loaded and processed at startup using the PROCESS HTML TAGS command and then saved as the live Backup.XML in the Preferences\Backup folder — keeping all format-specific knowledge in the template file rather than hard-coded in 4D method code. It documents the practical workflow: copy Backup.XML2 instead of Backup.XML when deploying, check for the file's existence in the On Startup/On Server Startup database method (locating the Preferences folder efficiently via the Extras folder path rather than the Structure path), and use Test path name to detect whether initialization is needed; if the Backup.XML file is missing, the developer can either silently generate one from hard-coded values, prompt the user to pick a folder, or surface a full Advanced Backup Settings dialog (a working example of which is provided in the sample database) covering nearly all standard 4D Backup preferences options. The note concludes with a full reference table mapping every settings variable (e.g., BKP_NbMinWait, BKP_at_CompressionRate, BKP_rbSched_Weeks) to its corresponding Backup.XML tag name (e.g., <Timeout>, <CompressionRate>, <Weekly>), covering retry/timeout behavior, restore/log-integration automation, compression/redundancy/interlacing rates, segment sizing, included files, destination folders, and hourly/daily/weekly/monthly scheduling options. As a whole, the note is a practical, still conceptually sound templating pattern for pre-seeding application configuration files, tied specifically to the 4D Backup product's classic XML project file format of that era.
