Converting a 4D database to project mode moved hierarchical/dropdown lists out of the binary structure file and into a plain lists.json file under the Sources folder — a deliberate change enabling lists to be tracked in Git alongside other project-mode source files — but this note flags an important side effect: SAVE LIST silently does nothing when the application is running compiled (a .4DZ project) or as a remote client connected to 4D Server, because those runtime modes only have read access to the structure's JSON files, while Load list still works fine for reading. The note gives three conditions to check whether an app is affected (project mode, compiled or client-server execution, and actual use of SAVE LIST anywhere in the codebase) and, if all three apply, provides a migration path: a convertListsJSONToRecords project method that reads every entry out of lists.json and creates a corresponding record in a new Lists table (with LONGINT-reference lists stored via LIST TO BLOB into a BLOB field, and array/object-type lists converted to a Collection stored in an Object field), plus two drop-in replacement methods, loadList(listName) and saveList(listSource; listName), that query/update that Lists table instead of touching lists.json — giving full read-write list management regardless of compiled or client-server mode. A bundled sample database demonstrates the failure with the classic commands side by side with the working table-backed replacement.
