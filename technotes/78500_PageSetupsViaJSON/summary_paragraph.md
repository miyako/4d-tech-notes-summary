This tech note addresses a practical printing pain point in classic 4D forms: `GET PRINT OPTION` can only be called from inside a form's own method, making it hard to batch-inspect or edit page setups for many forms from a project method or menu item. The workaround combines the deprecated command `_O_PAGE SETUP` (which loads a named form's print settings context without requiring the form to be open) with `GET PRINT OPTION` to pull out each setting — paper size/orientation, scale, copies, destination, double-sided, spooler name, page range, and legacy GDI printing layer — into a plain object, which is then serialized to disk with `JSON Stringify` and `TEXT TO DOCUMENT` under a `Resources/pageSetups` folder. Two utility methods, `saveAllFormPageSetups` and `savePageSetupDefinition`, iterate over every project form (via `FORM GET NAMES`) and every table form (via `GET TABLE TITLES`) to export a JSON file per form, named by table/form. A companion `loadPageSetup` method reverses the process, parsing the JSON with `JSON Parse` and re-applying each value with `SET PRINT OPTION`, returning a success flag so a caller (e.g., `printAllProjectForms`) can conditionally call `Print form`. The advantage over the older `Print settings to BLOB` approach is that JSON files are human-readable and hand-editable in a text editor, unlike opaque BLOBs, making bulk print-setting management and version control much easier. This is positioned as a small but useful utility pattern for shops that need consistent, scriptable print configuration across many forms/reports.
