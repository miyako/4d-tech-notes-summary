This Tech Note by Josh Fletcher, Technical Support Engineer at 4D Inc., is Part 2 of a two-part series on advanced debugging in 4D 2004; while Part 1 (TN 06-32, referenced but not part of this batch) covered 4D's native debugging features (the debug/trace window, Runtime Explorer, debug log file, and error messages), Part 2 introduces a complementary technique based on custom text-file logging for situations where those built-in tools are unavailable or insufficient. The note frames three specific advantages of log-file-based debugging over interactive debugging tools: (1) pattern recognition — a log file can be filtered, compared across runs, or archived for later analysis, illustrated with a worked example of spotting a memory leak in a 4D-for-OCI plug-in integration by noticing "handle creation" log lines that are never matched by a "handle free" line; (2) detecting timing/synchronization problems — since attaching a debugger and hitting breakpoints inherently distorts an application's real-time behavior, a log file lets the developer observe the unmodified execution timeline after the fact, demonstrated with a contrived factorial-calculation example where a second process alters a shared interprocess variable mid-calculation, visible clearly in the log via distinct process IDs (PID tags); and (3) working in both interpreted and compiled databases — since most of 4D's native debugging tools (the debug/trace window, full Runtime Explorer functionality, many error messages) are unavailable or limited when running a compiled database, a custom log file remains fully functional regardless of compilation state, which is especially valuable when a bug only reproduces in the compiled build. The bulk of the note then documents the accompanying "4D Logger 2004-1" component (nicknamed "Logger"), released open-source for developers to adapt freely, which standardizes and formats debug log output. It introduces the concept of a per-process "stack level" (tracked and visualized via numeric indentation in the log, distinct from 4D's actual internal call stack) that increases when a method/function call is logged as starting and decreases when it ends, making nested call structure visually legible in the log text. It documents six categories of logging commands the component provides — before/after logging for functions (including parameters and return value) and procedures (without return value), start/end logging for methods (which does not adjust stack level, since these mark the boundaries of a method body rather than a call), and general-purpose "message" logging both with and without an associated stack level — each illustrated with concrete example log output showing process ID tags, stack-level numbers/indentation, and formatted before/after/start/end labels. The note's overall thesis is that combining Part 1's native 4D debugging tools with Part 2's custom logging technique gives 4D developers a comprehensive debugging toolkit for both interpreted and compiled applications.
