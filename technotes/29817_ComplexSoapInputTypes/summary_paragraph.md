This is the first of a two-part Tech Note by Dave Dell'Aquila, Senior 4D Evangelist at 4D, Inc., on generating properly formed complex SOAP input parameters for web services that expect them. It starts from 4D's Web Services Wizard, which analyzes a WSDL and, for RPC-style services (parameters listed individually with a direction, name, and SOAP type — illustrated with a public ZIP-code lookup service), auto-generates a proxy method that uses SET WEB SERVICE PARAMETER to 'park' each argument and CALL WEB SERVICE to send the request and retrieve results via GET WEB SERVICE RESULT. The note shows the actual SOAP XML envelope 4D builds for this case (`<mns:ZipCodes ...><Zip xsi:type="xsd:string">95128</Zip></mns:ZipCodes>`) and its response. It then contrasts this with Doc-style ('complex') web services, flagged in the Wizard's parameter list with a small icon, which expect a single input parameter that is itself an XML fragment (and may return a single XML output parameter) — illustrated with an email-validation web service whose SOAP body is `<s0:ValidateEmailAddress><s0:emailAddress>daved@4D.com</s0:emailAddress></s0:ValidateEmailAddress>`. For Doc-style calls, the developer is responsible for building just the contents of the SOAP-ENV:Body element themselves: the note shows converting a hand-built XML string to a BLOB with TEXT TO BLOB, passing it to the Wizard-generated proxy method (which itself calls CALL WEB SERVICE with the 'Web Service Manual' parameter so 4D inserts the BLOB's contents directly into the request body), and receiving the raw response BLOB back via GET WEB SERVICE RESULT for manual parsing. To help developers figure out the exact XML a target service expects, the note recommends using a generic online SOAP test client (soapclient.com/soaptest.html) that displays the full request before sending it. The note ends by promising Part 2 will cover deriving the required Doc-style XML structure directly from a service's WSDL.
