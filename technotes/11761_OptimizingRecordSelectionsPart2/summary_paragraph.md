This is Part 2 of a two-part Technical Note aimed at helping developers optimize the handling of record selections as their 4D data files grow larger and as more 4D Client or Web connections are added. Where Part 1 covered how a 4D data file is organized on disk and in memory, Part 2 shifts focus to the runtime concepts developers actually manipulate: the current record, the current selection, and named selections. The note discusses principles for using these concepts effectively so that performance remains acceptable even as data volume and concurrent user counts scale up — a practical concern for any growing 4D Client/Server deployment of the era. Because record selections (sets of matching records manipulated as a group, rather than one record at a time) are central to how 4D applications query, filter, sort, and report on data, understanding how to manage them efficiently was directly tied to application responsiveness and scalability. Though grounded in the specifics of 4D v6-era data file internals, the underlying set-based selection model and its optimization principles remain foundational to how 4D applications — including modern ORDA-based ones — think about efficiently working with subsets of data.
