This Tech Note by Olivier Deschanels (4D, S.A.) opens a series on 4D's internal data-file structure by first contrasting 4D's single-file data storage (one `.data`/`.4DD` file since Version 2, versus a separate file per table/index used by many multi-file database architectures) and arguing its advantages: simpler backup ("copy one file"), no risk from misplaced auxiliary files, avoidance of operating-system open-file-count limits, and engine-managed (rather than OS-level) fragmentation. It then explains that the data file is organized into fixed 128-byte blocks, and that every record occupies at least one block (and always a multiple of 128 bytes), consisting of a 22-byte header (record marker, checksum, cache save data, table/record number, sizes, indicators), a per-record "microstructure" (4 bytes per field: type plus offset) that acts like a snapshot of the table structure at the time the record was last saved, and the actual variable-length field data with no padding. Because the microstructure is compared against the current table structure only when a record is loaded, structure changes (adding a field, changing a field's type) cost nothing until existing records are actually accessed and re-saved — but this same mechanism is why fields can never be deleted in 4D's classic engine, only converted, since removing a field would make the microstructure and structure permanently disagree. The note demonstrates using `APPLY TO SELECTION([Table];[Table]field:=[Table]field)` to force an entire selection to pick up a pending structure/type change immediately, e.g., before running a search that depends on the new type.
