This Tech Note (TN 01-29, 4D v6.7, Mac & Win, published June 30, 2001) presents a description of the internal byte-level structure of 4D's records within its data files. Only a short on-page teaser paragraph survives in this archive rather than the full downloadable PDF and example database, because the original download was an old Windows self-extracting .exe installer (https://kb.4d.com/ftp://ftp.4D.com/ACI_TECHNICAL_NOTES/2001/Windows/TN_2001_26-30_(JUN)/01-29_The_128th_Byte.exe) that could not be extracted in this environment; the original 4D Tech Notes site offered separate Windows and Mac downloads of the complete note and its companion example database, but neither is retrievable here. Based on the surviving teaser text, the note's proposition is: This article describes the internal structure of 4D's records. With this knowledge, you will be able to optimize the access to your data and better understand 4D's inner workings.

In order to store data, databases use specific files saved on a hard disk (or any other data storage device). Generally, database management systems use one file per table. In addition to that, they also need an additional file for each index (when developers have control over that parameter), or, in some cases, to describe a relation between two tables. This architecture's main advantage is to prevent you from mixing "apple and oranges" but it also quickly increases the number of disk files and it makes installations, updates, and backup increasingly difficult. Its featured technology centers on 4D internal record structure, Database file architecture fundamentals, reflecting typical concerns of the 4D 6.7 (4D 2000/2001 era) developer community working in binary Design Mode on classic Mac OS/early Mac OS X and Windows 98/2000/NT. This note describes the internal byte-level structure of 4D's records within its data files, aimed at helping developers optimize data access and understand 4D's inner workings, including general database-architecture tradeoffs (one file per table plus per-index files versus a consolidated format). Because 4D's on-disk record and data-file format has been re-engineered multiple times in the decades since (v11 SQL engine, then the 64-bit engine), the specific byte-level structure detailed in this note no longer matches any current 4D file format, making it a historical snapshot of early 4D internals rather than a practical reference.
