Written by Jean-Yves Fock-Hoon, 4D's QA Manager, this Tech Note explains how 4D's architecture handles CPU time allocation across its internally emulated processes, so developers can use that understanding to speed up their databases. It covers the Database Properties CPU usage setting (Low/Normal/High) and the underlying SET DATABASE PARAMETER selectors (10, 11, 12) that let developers fine-tune CPU tick allocation separately for 4D stand-alone, 4D Server, and 4D Client, explaining the tradeoffs of vMinTicks/vMaxTicks/vNbTicks values including their effect on OS responsiveness and Client/Server connection stability. It then explains 4D's own cooperative scheduler in detail: 4D processes must periodically "call back" the scheduler to yield CPU time to other processes, which happens automatically in interpreted mode after most commands but must be manually triggered with the IDLE command (or forced via DELAY PROCESS (0)) in compiled mode, especially inside tight loops, since compiled code otherwise never yields. The note explains why executing IDLE too frequently wastes CPU (each call may consume less than a full scheduler tick, causing rapid useless handoffs), and recommends process pooling — pausing and reusing idle processes rather than repeatedly creating/deleting them — as a way to avoid the real CPU and memory cost of process allocation, which is especially expensive in Client/Server configurations with large variable tables. It connects mismanaged scheduling directly to real symptoms developers would recognize, including 4D Client's -10001/-10002 timeout errors when either side of a Client/Server connection becomes too CPU-starved to respond in time. Finally, it closes with general performance guidance on avoiding excessive field indexing and overly complex triggers, both of which multiply the CPU cost of routine record updates across many processes.
