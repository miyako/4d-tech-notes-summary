This Tech Note demystifies 4D's internal Scheduler, the mechanism that has always managed how 4D processes multitask, even after the v11 SQL data engine was rewritten to be multithreaded for multi-core support — since 4D language code itself remains a single, non-thread-safe cooperative execution model. It presents the Scheduler as an endless loop with two jobs: checking for system events to relay to 4D processes, and giving CPU time to each active process, illustrated with pseudocode. The note explains the three user-tunable values exposed through SET DATABASE PARAMETER — min_ticks (how long 4D yields to the system when busy), max_ticks (how long it yields when idle), and ticks_between (how long 4D holds the CPU between system calls) — detailing the tradeoffs of increasing or decreasing each, plus equivalent Preferences settings (Average to 4D, Max to 4D, Max to Other Apps). It also covers processor usage considerations including multi-processing and "processor spoofing," a side effect of certain tick settings. Throughout, the note stresses that developers rarely need to tweak these defaults, but that understanding them helps in the rare cases where the defaults aren't optimal, such as diagnosing unexpectedly high CPU usage or poor responsiveness.
