This Tech Note by Jean-Luc Pellerin (Training Manager, 4D SA) demonstrates how to implement a two-level drill-down browser interface using 4D's hierarchical list commands, illustrated with a `[Customers]` database organized by Region and County. On startup, an interprocess variable `◊LH` holding the list reference is initialized, the current list (if any) is cleared with `CLEAR LIST`, and a new hierarchical list is created with `New list`, populated at the top level from an array of distinct region names obtained via `DISTINCT VALUES([Customers]Region;$T_Region)` and added one by one with `APPEND TO LIST`. When a user clicks an item, the code determines whether it is a top-level region or a nested county by walking up the hierarchy with `List item parent` in a `While` loop counting levels; for a region click, it queries `[Customers]` by that region, builds a county sublist from `DISTINCT VALUES([Customers]County;...)` only if it doesn't already exist, and attaches it to the parent item with `SET LIST ITEM` before calling `REDRAW LIST`, while a county click simply re-queries by the county value. The note explains why `◊LH` is declared as an interprocess (not process) variable -- so the list exists only once rather than being duplicated per process -- and stresses that `DELETE LIST(◊LH;*)` must be called when exiting the form (with the `*` parameter to also delete attached sublists), otherwise the list reference is freed but the list itself leaks in memory.
