This tech note addresses a common pain point in production 4D deployments: enabling diagnostic logging in compiled applications previously required code changes and a recompile, which is impractical when troubleshooting a live incident. Starting in 4D v19 R3, administrators can instead drop a logConfig.json file — validated against a documented JSON Schema — onto the 4D Server maintenance tab's "Load log configuration file" button to toggle request logs, debug logs (with an optional per-command allow/deny list keyed by 4D command numbers such as 277/QUERY and 341/QUERY SELECTION), diagnostic logs, HTTP debug logs (equivalent to WEB SET OPTION(Web debug log; ...)), and POP3/SMTP/IMAP/ORDA logs, all without restarting the server. The forceLoggingConfiguration flag lets the JSON file override whatever logging state code or the admin UI had set, which is valuable for standardizing settings across many sites running independent 4D Server instances by simply distributing the same file. The note complements this built-in mechanism with external tooling: ProcDump on Windows and the native macOS ~/Library/Logs/DiagnosticReports folder for crash dumps, and the community Info Reports component for periodic snapshots of connections, processes, and memory usage. It closes with a practical matrix mapping four common support scenarios — crashing on Windows, crashing on macOS, application hangs, and network instability — to the specific combination of logs and tools to enable for each, aimed at giving both customers and 4D technical support a faster, more complete diagnostic package.
