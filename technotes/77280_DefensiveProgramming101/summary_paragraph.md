This Tech Note by Timothy Aaron Penner is a practical, example-driven catalog of common defensive-programming mistakes in 4D and the fixes for each. It opens with the classic array-bounds problem — accessing an array element without first checking `Size of array`, which triggers an "Indice out of range" runtime error — and shows the corrected, guarded version. It then covers character-reference symbol pitfalls (`[[..]]`), unchecked listbox row selections, validating parameters actually passed into a method before using them, checking a pointer's type before dereferencing it, and re-initializing array variables defensively rather than assuming prior state. A recurring theme across several sections — SVG, XML, Lists, and Named Selections — is the question of whether a variable holds actual data or merely a reference/handle to data that may no longer be valid, illustrating each with concrete before/after code; for Named Selections specifically it explains when `CLEAR NAMED SELECTION` is required to free memory versus when a selection created via `CUT NAMED SELECTION` and consumed via `USE NAMED SELECTION` no longer needs explicit clearing. The "Other areas to look out for" section addresses validating file and folder paths with `Test path name` before passing them to commands like `Read Picture file`, `Open Document`, `DOM Parse XML Source`, or `Document to Blob`/`Document to Text`, plus cautions around looping over table or field numbers that may not correspond to valid structure elements. Throughout, the note's running theme is that code which "works fine on the developer's machine" frequently fails for customers due to unvalidated assumptions, and that a handful of simple guard checks — sizes, types, path validity, reference liveness — prevent the majority of these failures. The conclusion reinforces defensive programming as a core discipline every 4D developer should internalize rather than an optional add-on.
